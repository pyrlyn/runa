## Scope

- Crates: `runa` (CLI, `serve`, `daemon`, `pull`, `mcp`, `config`, `tasks`),
  `runa-fit` (`gguf`, `remote`), `runa-memory` (`registry`), and
  `runa-engine` (`generate`, `load`), covering the paths that `serve` and
  `run` call.
- Focus: wrong implementations, missing input/argument checks, missing
  error handling, anything that reliably errors or breaks, and basic
  security (secret handling, path handling, temp files, local IPC).
- Out of scope: kernels (`runa-kernels`), cloud adapters' live APIs
  (no keys), the `mtmd`/`mistralrs` feature builds, Windows/Linux runtime.
- Not re-reported: hostile-GGUF-header crashes (huge `n_dims`
  reservation, `block_count` OOM, unchecked `u64` math in
  fit/planner/speed). These are fixed or recorded in open PR #23
  (`test/cargo-fuzz`). On `main` a 37-byte header with `n_dims = u32::MAX`
  returned `UnexpectedEof` without aborting on macOS (lazy allocation), so
  this audit did not confirm that one on this host.

### 1. `serve`/`run` abort on a prompt longer than the effective batch when `--ctx` < 512

- Severity: high
- Impact: any HTTP client can kill `runa serve` with one request. The
  process aborts in C (`GGML_ASSERT`), so the `catch_panic` middleware
  cannot help. Every in-flight request is lost and the server stays down
  until restarted. The same prefill code backs `runa run`/`chat`, so a long
  prompt with a small `--ctx` aborts there too.
- Environment: macOS 27.0 arm64, debug build, `qwen2-0_5b-instruct-q4_0.gguf`.
- Steps to reproduce:
  1. `runa serve qwen2-0_5b-instruct-q4_0.gguf --port 18740 --ctx 128`
  2. POST `/v1/chat/completions` with one user message of `"hello world " * 400`
     and `max_tokens: 4`.
  3. `curl localhost:18740/health`
- Expected: HTTP 400 (prompt exceeds context) and the server keeps running.
- Actual: the connection drops (curl `HTTP=000`), the process is gone, and
  `/health` cannot connect.
- Evidence (server stderr):
  ```text
  llama-cpp-sys-2-0.1.133/llama.cpp/src/llama-context.cpp:1441: GGML_ASSERT(n_tokens_all <= cparams.n_batch) failed
  ... llama_decode ... runa_engine::generate::Generation::prefill_step ...
  ```
  llama.cpp clamps the context's `n_batch` to `n_ctx` (128). runa still
  chunks the prefill by `LoadConfig::n_batch` (512).
- Suggested fix: clamp `n_batch`/`n_ubatch` to `n_ctx` in `LoadConfig`
  before the context is created, and chunk prefill by that clamped value.
  Also reject `prompt_tokens.len() >= n_ctx` before prefill (see #8).
- Missing check / error handling: `crates/runa-engine/src/load.rs:876-878`
  (`n_batch` not clamped to `n_ctx`);
  `crates/runa-engine/src/generate.rs:524-526` (`batch_size` uses the
  unclamped config); `crates/runa-engine/src/generate.rs:330-333` (no
  prompt length check, only `saturating_sub`).

### 2. `HF_TOKEN` is sent as a Bearer token to any host given to `runa fit`

- Severity: high
- Impact: a user with `HF_TOKEN` exported who runs
  `runa fit https://<any-host>/x.gguf` (a link from a README, chat or
  issue) sends their Hugging Face token to that host. The token may grant
  write access to the user's HF repos.
- Environment: macOS 27.0 arm64; loopback Python HTTP server that logs headers.
- Steps to reproduce:
  1. Serve `tests/fixtures/synthetic-llama.gguf` on `127.0.0.1:18731` with
     a server that logs the `Authorization` header.
  2. `HF_TOKEN=hf_DUMMY_QA_TOKEN XDG_CACHE_HOME=$tmp runa fit http://127.0.0.1:18731/evil/model.gguf`
- Expected: the token is sent only to `huggingface.co` (and the Hub API base).
- Actual: the server receives it.
- Evidence: `REQ /evil/model.gguf Range=bytes=0-8388607 Authorization=Bearer hf_DUMMY_QA_TOKEN`
- Suggested fix: add `Authorization` only when the request host is
  `huggingface.co` (or the configured hub/API host). Keep reqwest's
  default of stripping it on cross-host redirects.
- Missing check: `crates/runa-fit/src/remote.rs:235-241` (`authed()` has no
  host check); it is called for arbitrary URLs from `get_range`
  (`remote.rs:401-405`), via `fetch_url`/`probe` (`remote.rs:322-457`).

### 3. `runa tasks claim` has no cross-process lock

- Severity: high (the registry exists to stop double claims between agents)
- Impact: two agents claiming the same task at the same time both get
  "claimed", so both work on it. The read-modify-write is not atomic, so
  the file can also be left torn (a dangling `|` line).
- Environment: macOS 27.0 arm64, temp registry via `RUNA_TASK_REGISTRY`.
- Steps to reproduce:
  1. Write a registry with one row `| P1.1 | free |  |  |`.
  2. Run `runa tasks claim P1.1 --agent alice` and
     `runa tasks claim P1.1 --agent bob` in parallel; check both exit codes.
  3. Repeat 30 times.
- Expected: exactly one claim succeeds; the other gets `AlreadyClaimed`.
- Actual: both succeeded in 30/30 runs. The final file had
  `| P1.1 | in progress | bob | … |` followed by a stray `|` line.
- Evidence: `both succeeded in 30/30 runs`
- Suggested fix: take an OS file lock (`flock`/`fs2`/`fd-lock`) on the
  registry (or a sidecar `.lock`) around read → check → write. Write via
  temp file + `rename` so the update is atomic.
- Missing check: `crates/runa-memory/src/registry.rs:49-56,83,109` (only an
  in-process `Mutex`, which does nothing across CLI processes);
  `registry.rs:133-137` (non-atomic `fs::write`).

### 4. `tasks claim/release` accept any agent string and corrupt the table

- Severity: medium
- Impact: an agent name with `|` breaks the markdown row, after which a
  different agent can release the claim. An empty name produces an
  `in progress` row that `scripts/lint-tasks.py` rejects, so CI goes red.
- Environment: as #3.
- Steps to reproduce:
  1. `runa tasks claim P1.1 --agent 'a|b'` → row `| P1.1 | in progress | a|b | … |`.
  2. `runa tasks release P1.1 --agent a` → `released P1.1` (exit 0).
  3. On a fresh file: `runa tasks claim P1.1 --agent ''` → `claimed P1.1 as  at …`;
     `python3 scripts/lint-tasks.py` → `error: P1.1: in-progress claim without agent`.
- Expected: names that are empty, contain `|`, or contain a newline are
  rejected with an error.
- Actual: they are accepted (see above).
- Suggested fix: validate `agent` (non-empty after trim, no `|`, no control
  characters) in `TaskRegistry::claim`/`release`. The clap argument could
  also check it.
- Missing check: `crates/runa-memory/src/registry.rs:82` (claim) and `:108`
  (release); the CLI passes `--agent` through unchanged.

### 5. Task registry reports every I/O error as "task not found"

- Severity: medium
- Impact: a missing, unreadable or read-only registry gives
  `runa: error: task not found`. Agents conclude the task id is wrong when
  the real problem is the path or the permissions.
- Steps to reproduce:
  1. `RUNA_TASK_REGISTRY=/tmp/nope.md runa tasks claim P1.1 --agent qa`
  2. `chmod 444 reg.md; RUNA_TASK_REGISTRY=reg.md runa tasks claim P1.1 --agent qa`
- Expected: `cannot read /tmp/nope.md: No such file or directory` and
  `cannot write reg.md: Permission denied`.
- Actual: `runa: error: task not found` (exit 1) both times.
- Suggested fix: add `ClaimError::Io(String)` and map `read_rows` /
  `write_rows` errors to it. `list_free`/`status` should also stop
  swallowing errors (`unwrap_or_default`, `.ok()?`).
- Missing error handling: `crates/runa-memory/src/registry.rs:84,100,110,124`
  (`map_err(|_| ClaimError::NotFound)`), `:65`, `:76`.

### 6. `serve` `image_url` accepts local paths (file-existence oracle)

- Severity: medium (low while bound to 127.0.0.1; higher with `--host 0.0.0.0`)
- Impact: any client of the HTTP API can probe for any path on the server
  host, because existing and missing paths get different errors. With the
  `mtmd` feature, the server also opens any readable local file as an
  image for the model. The probe works on builds without `mtmd` too,
  because the path check runs before the feature gate.
- Steps to reproduce:
  1. `runa serve qwen2-0_5b-instruct-q4_0.gguf --port 18740`
  2. POST a chat with `{"type":"image_url","image_url":{"url":"/etc/hosts"}}`
  3. Same request with `"/Users/listepo/.ssh/id_nonexistent"`
- Expected: the HTTP API rejects local paths (accepts `data:` only, as the
  remote-URL error message suggests), or allows them only under an opt-in
  directory. The error should be the same whether or not a file exists.
- Actual: `/etc/hosts` → `image_url / vision content requires rebuilding runa with --features mtmd`
  (400); the missing path → `image_url path not found: /Users/listepo/.ssh/id_nonexistent` (400).
- Suggested fix: refuse plain paths in `image_url_to_path` for HTTP
  requests (or check them against an `--allow-image-dir`), and run the
  `mtmd` gate before any decoding or filesystem access.
- Missing check: `crates/runa/src/serve.rs:1224-1229` (no path policy);
  the feature gate at `serve.rs:1152` runs only after `content_text` at
  `serve.rs:1110`.

### 7. `serve` leaks request payloads as world-readable temp files

- Severity: medium
- Impact: every `data:` image request writes its payload to the temp dir
  and never deletes it, even when the request is rejected. Failed
  `input_audio` decodes and failed transcriptions also leave files.
  Requests can be up to 32 MiB, so repeated requests fill the disk. The
  files are created `0644` with predictable names
  (`runa-img-<pid>-<nanos>`), so other local users can read users' images
  and audio.
- Steps to reproduce:
  1. Run the server as in #6, on a build without `mtmd`.
  2. POST `image_url` with `data:image/png;base64,aGVsbG8=` → 400 (mtmd gate).
  3. POST `input_audio` with `{"data":"UklGRg==!!!not-base64###","format":"wav"}` → 400 decode error.
  4. `ls -la $TMPDIR | grep runa-`
- Expected: no files left after the request ends; files created `0600`
  (or kept in memory).
- Actual:
  ```text
  -rw-r--r--  1 listepo staff 5 Oct  2 01:31 runa-img-50912-1790893894212708000
  -rw-r--r--  1 listepo staff 4 Oct  2 01:31 runa-in-audio-50912-1790893894565839000.wav
  ```
- Suggested fix: use `tempfile::NamedTempFile` (0600, deleted on drop) and
  keep the guard alive until generation ends. Run the feature gate before
  writing anything (#6).
- Missing error handling / cleanup: `crates/runa/src/serve.rs:1219`
  (image file never removed); `serve.rs:1239-1246` (`?` on rename/decode
  skips `remove_file`); `serve.rs:521-531` (`?` on `transcribe_file` skips
  `remove_file`); `serve.rs:535-546` (default permissions, plain
  `fs::write` follows symlinks).

### 8. Context overflow is an opaque HTTP 500; no prompt length check

- Severity: medium
- Impact: clients get `500 decode error: NoKvCacheSlot` for a plain
  client-side problem (prompt too long). OpenAI SDKs retry 5xx responses,
  so the same oversize prompt is re-run several times. When `ctx` < 512
  the same input aborts the process instead (#1).
- Steps to reproduce:
  1. `runa serve qwen2-0_5b-instruct-q4_0.gguf --port 18741 --ctx 1024`
  2. POST a chat with `"hello world " * 800` (about 2400 tokens).
- Expected: HTTP 400 `context_length_exceeded` naming the prompt token
  count and `n_ctx`.
- Actual: `decode error: NoKvCacheSlot` HTTP 500; stderr has
  `decode: failed to find a memory slot for batch of size 512`.
- Suggested fix: tokenize, then check `prompt_tokens >= n_ctx`. Return a
  typed `EngineError::ContextExceeded` and map it to 400 in `serve` and
  the daemon. Optionally cap `max_tokens` at `n_ctx - prompt`.
- Missing check: `crates/runa-engine/src/generate.rs:330-333`;
  `crates/runa/src/serve.rs:340-342` (all engine errors map to 500).

### 9. `finish_reason`/`stop_reason` ignore truncation by `max_tokens`

- Severity: medium
- Impact: clients cannot tell a truncated answer from a complete one.
  OpenAI/Anthropic SDK code that checks `finish_reason == "length"` (or
  `stop_reason == "max_tokens"`) to continue or warn never triggers.
- Steps to reproduce: POST `{"messages":[{"role":"user","content":"Write a long story about a cat"}],"max_tokens":3}`
  to `/v1/chat/completions`, then to `/v1/messages`.
- Expected: `"finish_reason":"length"` and `"stop_reason":"max_tokens"`.
- Actual: `{"finish_reason":"stop", … "content":"Once upon a" … "completion_tokens":3}`
  and `"stop_reason":"end_turn"`.
- Suggested fix: carry the `GenEvent::Done(StopReason)` value into the
  response builders and map `MaxTokens` → `length`/`max_tokens`.
- Wrong implementation: `crates/runa/src/serve.rs:646` and `:947` drop
  `Done(_)`; `serve.rs:619-623`, `:675`, `:975-981` derive the reason only
  from tool calls.

### 10. A second `runa daemon` unlinks a live socket

- Severity: medium
- Impact: starting a second daemon (a launchd/systemd restart race, or a
  manual start) silently orphans the first one. That daemon keeps its
  model in RAM (~820 MB RSS each here) with no reachable socket. When the
  orphan later exits, it deletes the new daemon's socket, so `run`/`chat`
  quietly fall back to in-process loads. The code comment says "a live one
  fails the bind below", but the code removes the socket first, so the
  bind never fails.
- Steps to reproduce:
  1. `runa daemon qwen2.gguf --socket /tmp/d.sock` (A); `ls -li /tmp/d.sock`.
  2. Start the same command again (B); `ls -li /tmp/d.sock` → new inode; both PIDs alive.
  3. SIGINT A → `/tmp/d.sock` is gone while B still runs.
- Expected: B fails with "daemon already running on /tmp/d.sock".
- Actual: B binds (inode 1920361599 → 1920363265), both processes run, and
  after A exits: `ls: d.sock: No such file or directory`, B alive.
- Suggested fix: before removing, try `UnixStream::connect`. Remove only on
  `ECONNREFUSED`/`ENOENT`, otherwise error out. On shutdown, remove the
  socket only if its inode still matches the one this daemon bound.
- Missing check: `crates/runa/src/daemon.rs:156-158` (unconditional
  `remove_file`) and `daemon.rs:189` (unconditional removal on exit).

### 11. `runa fit` URL fetch buffers whole bodies and never checks `Content-Range`

- Severity: medium
- Impact: when a server ignores `Range` (some CDNs, proxies, plain
  servers), `runa fit <url>` downloads the whole multi-GB model into RAM
  before applying `MAX_HEADER_BYTES` (256 MiB), bounded only by the 60 s
  timeout. A 206 body is also unbounded, and its start offset is never
  checked, so a server that returns `bytes 0-…` again gets duplicate bytes
  appended and a wrong parse.
- Steps to reproduce:
  1. Serve a 400 MiB file (synthetic-llama header + zeros) with a server
     that answers every request `200` with the whole body.
  2. `/usr/bin/time -l runa fit http://127.0.0.1:18732/m.gguf`
- Expected: stop reading after `MAX_HEADER_BYTES` (or as soon as
  `Content-Length` shows it is too big); peak RSS stays small.
- Actual: `runa: error: header incomplete after 0 bytes (server does not serve byte ranges)`,
  `1290862592 maximum resident set size` (1.29 GB for a 400 MiB body).
- Suggested fix: reject early on `Content-Length > MAX_HEADER_BYTES`. Read
  the body with `take(MAX_HEADER_BYTES + 1)`. For 206, parse
  `Content-Range` and require `start == from`, and cap the body at
  `want - from`.
- Missing check: `crates/runa-fit/src/remote.rs:432-444` (`resp.bytes()` with
  no cap), checked too late at `remote.rs:359-369`;
  `remote.rs:421-431` (206 accepted without a start/length check).

### 12. `[memory]` and `[audio]` ignore "later files win"; bad env values ignored

- Severity: medium
- Impact: `docs/config.md:3` says "later files win" (`./runa.toml` over
  `~/.config/runa/config.toml`), and `threads`, `on_unfit` and
  `max_load_percent` follow that. But `[memory]` and `[audio]` take the
  first file that has the table, so a project's `runa.toml` cannot
  override them. Separately, invalid `RUNA_MEMORY_IDLE_TIMEOUT_S`,
  `RUNA_MEMORY_FLOOR_MIB` and `RUNA_MEMORY_MAX_GROWTH_MIB` values are
  ignored silently, while `RUNA_THREADS` and others raise an error.
- Steps to reproduce (temporary unit test, reverted):
  1. Set HOME so that `~/.config/runa/config.toml` has `[memory] idle_timeout_s = 111`,
     `[audio] route = "asr"` and `[defaults] threads = 3`.
  2. In the working directory, `./runa.toml` has `idle_timeout_s = 222`,
     `route = "native"` and `threads = 5`.
  3. Call `resolve_threads(None)`, `resolve_memory_policy()` and
     `resolve_audio_route(None)`; then set `RUNA_MEMORY_IDLE_TIMEOUT_S=ten`.
- Expected: threads 5, idle 222, audio native; the bad env value is an error.
- Actual: `QA threads=Some(5) (project=5) idle_timeout_s=111 (project=222) audio=Asr (project=native)`,
  then `QA RUNA_MEMORY_IDLE_TIMEOUT_S=ten -> Ok, idle_timeout_s=111`.
- Suggested fix: iterate all files and let later ones override (as
  `load_on_unfit` does). Parse the `RUNA_MEMORY_*` vars with an error, as
  `RUNA_THREADS` does.
- Wrong implementation / missing check: `crates/runa/src/config.rs:505`
  (`return` on first file), `config.rs:519` (`break` on first file),
  `config.rs:522-536` (`if let Ok(n) = s.parse()` drops errors).
  `read_config_text` (`config.rs:97-100`) also treats an unreadable or
  non-UTF-8 file as missing.

### 13. MCP `tool_loop` runs `max_rounds + 1` tool rounds and discards the last

- Severity: medium
- Impact: `--max-tool-rounds N` runs tools N+1 times. The results of the
  last round never reach the model, so side-effecting tools (write a file,
  send a request) run once more than allowed, for nothing.
  `--max-tool-rounds 0` still runs one round of tools before failing.
- Steps to reproduce (temporary unit test, reverted): call `tool_loop`
  with a step that always returns one call, and count `call` invocations.
- Expected: at most N executions; with N = 0, none (error, or answer without tools).
- Actual: `QA max_rounds=0 -> tools executed 1 times, result Err("no answer after 0 tool rounds …")`
  and `QA max_rounds=2 -> tools executed 3 times, result Err(…)`.
- Suggested fix: check the round budget before running the calls (fail
  once `round == max_rounds` and calls are not empty), or loop `0..max_rounds`
  plus a final no-tools step.
- Wrong implementation: `crates/runa/src/mcp.rs:263-276`.

### 14. Model store directory collides for different repos

- Severity: low
- Impact: `repo_dir` maps `/` to `-`, so `org/model-GGUF` and
  `org-model/GGUF` share one directory. `runa run hf:org-model/GGUF:Q4_K_M`
  can then resolve a file pulled from a different repo (offline lookup
  does not check the repo). The module docs promise `<owner>--<name>`.
- Steps to reproduce (temporary unit test, reverted):
  `repo_dir("org/model-GGUF")` vs `repo_dir("org-model/GGUF")`.
- Expected: different directories, named `owner--name` as documented.
- Actual: both `…/runa/models/org-model-GGUF`.
- Suggested fix: use the documented `owner--name` layout (the Hub rejects
  `--` inside repo ids, so the mapping is unambiguous), or escape `-`.
  Changing the layout needs a migration or fallback lookup for existing stores.
- Wrong implementation: `crates/runa/src/pull.rs:47-58` versus the doc at `pull.rs:4`.

### 15. `serve` base64 decoder accepts invalid input

- Severity: low
- Impact: corrupt `data:` URIs and `input_audio` payloads are "decoded"
  into garbage, and a later decoder fails with a confusing message instead
  of `invalid base64`. Everything after the first `=` is ignored, and a
  dangling single character is dropped.
- Steps to reproduce: POST `input_audio` with `"data":"UklGRg==!!!not-base64###"`.
- Expected: 400 `invalid base64`.
- Actual: 400 `decode: unsupported feature: core (probe): no suitable format reader found`
  (a 4-byte `RIFF` file was written, see #7).
- Suggested fix: use the `base64` crate (already in the dependency tree)
  with the standard engine, or reject non-padding bytes after `=` and
  `n == 1` leftovers.
- Missing check: `crates/runa/src/serve.rs:1264-1290`.

### 16. GGUF reader ignores `general.alignment`

- Severity: low (`data_start` is not used outside `gguf.rs` today)
- Impact: `Reader::data_start` is wrong for files with a non-default
  alignment, and anything that seeks to tensor data later reads the wrong
  bytes. The comment says "64-byte alignment" while the code uses 32.
- Steps to reproduce (temporary integration test, reverted): build a v3
  header with `general.name` and `general.alignment = 64` (header end 92).
- Expected: `data_start = 128`.
- Actual: `QA alignment=64: header end=92 data_start=96`.
- Suggested fix: read `general.alignment` (u32, power of two, non-zero),
  falling back to 32.
- Wrong implementation: `crates/runa-fit/src/gguf.rs:336-341`.

### 17. `/v1/embeddings` `usage` counts whitespace words, not tokens

- Severity: low
- Impact: wrong usage accounting for clients that bill or budget by tokens.
- Steps to reproduce: POST `/v1/embeddings` with `"antidisestablishmentarianism"`.
- Expected: the tokenizer's token count (several tokens).
- Actual: `{'prompt_tokens': 1, 'total_tokens': 1}`.
- Suggested fix: return the token count from `embed` and sum it.
- Wrong implementation: `crates/runa/src/serve.rs:456`.

### 18. Chat endpoints accept any `role` and `max_tokens: 0` silently

- Severity: low
- Impact: typos such as `"role":"assitant"` are passed to the chat
  template and silently change the prompt. `max_tokens: 0` returns 200
  with empty content, where OpenAI returns 400.
- Steps to reproduce: POST `{"messages":[{"role":"wizard","content":"hi"}],"max_tokens":3}` → 200 with a reply;
  POST with `"max_tokens":0` → 200, `content: ""`.
- Expected: 400 for an unknown role, and for `max_tokens < 1`.
- Suggested fix: validate the role against
  `system|developer|user|assistant|tool` and require `max_tokens >= 1`.
- Missing check: `crates/runa/src/serve.rs:1140-1146` and `serve.rs:300-303`
  (same for `/v1/messages` at `serve.rs:379`).

### 19. `pull` writes the `.verified` sidecar before the size-limit check

- Severity: low (code inspection; needs a Hub response without `x-linked-size`)
- Impact: when the Hub omits `x-linked-size`, the pre-download size check
  is skipped. `verify_downloaded` then writes the `.verified` sidecar before
  `check_size_limit(len)` fails, so the over-limit file stays on disk,
  marked verified, and the next `pull` returns it as a cache hit. A size
  mismatch also leaves the bad file on disk (only an SHA mismatch removes it).
- Suggested fix: check the size limit before writing the sidecar, and
  remove the file on any verification failure.
- Missing check / cleanup: `crates/runa/src/pull.rs:265-266`, `pull.rs:279-287`.

### 20. `ModelPool` lock is held for a whole model load (suspected)

- Severity: low (suspected, not timed)
- Impact: with several models in `serve`/`daemon`, loading or reloading one
  model (seconds for multi-GB GGUFs) blocks every request to other
  already-loaded models. `ensure_engine` runs under the global
  `Mutex<ModelPool>` and waits on `ready_rx` for the load to finish.
  `/health` is unaffected.
- Suggested fix: reserve a "loading" slot under the lock, drop the lock
  while `spawn_engine` loads, then insert the sender (or use a per-model
  `OnceCell`).
- Location: `crates/runa/src/serve.rs:224-231`, `crates/runa/src/pool.rs:394-430`,
  `pool.rs:505-507`.
