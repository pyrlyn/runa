# Внутреннее устройство fit-проверки

Формулы, оценщики и калибровка для `runa fit` (план P1, решения
D5/D6). Разделы об оценщиках появляются вместе со своими задачами (P1.5 вычислительный буфер,
P1.9 модель скорости); этот файл начинается с CLI и пути чтения удалённого
заголовка (P1.2).

## CLI

```sh
runa fit hf:unsloth/Qwen3-8B-GGUF:Q4_K_M --ctx 16384 --kv q8_0
runa fit ./model.gguf --json
runa fit --recommend --use code --top 3
runa fit --recommend --offline
```

`runa fit <model>` принимает локальный GGUF, псевдоним, `hf:<repo>:<file-or-quant>`
или URL http(s). Скачанная копия читается с диска; для всего остального загружается
только заголовок. Команда выводит отчёт с вердиктом (таблица памяти, декодирование,
префилл, TTFT, предупреждения, советы) и завершается с кодом `0` (помещается), `1` (помещается с
предупреждениями) или `2` (не помещается). `--json` выводит те же числа одним объектом.
Соседний `mmproj-*.gguf` локальной модели учитывается. `--rpc host:port,…`
(P9.3) оценивает только локальное размещение: без фичи cargo `rpc`
выводится явное предупреждение, с ней — примечание, что удалённая память не
учитывается; `runa run --rpc … --device RPC0` обращается к серверам при загрузке.

`--recommend` параллельно проверяет каждую модель из встроенного каталога
(`crates/runa-fit/src/catalog.toml`, `runa_fit::recommend`) и
выводит лучшие `--top` (по умолчанию 5), каждую со ссылкой для `runa pull`. Записи с NO FIT
отбрасываются. Остальные ранжируются так:

1. сначала пригодная скорость (прогнозируемое декодирование ≥ 5 tok/s),
2. затем уровень качества (от 1 — маленькая … до 4 — лучшая в каталоге),
3. затем прогнозируемая скорость декодирования в tok/s.

`--use chat|code|vision|reasoning` оставляет модели, помеченные для этого применения;
с `vision` учитывается размер проектора. Заголовки кешируются после первого
запуска (см. ниже). `--offline` не требует сети: он сравнивает размер файла из каталога
(+ проектор) с VRAM за вычетом запаса, иначе с RAM, и прогнозирует
декодирование по пропускной способности памяти и активным байтам (записи MoE хранят их). KV
и вычислительные буферы офлайн не учитываются, а скорости выводятся с `~`.
Неудачная проба выводит `skip <name>: <error>` в stderr. Если ничего не помещается,
код выхода `2`.

Каталог содержит только однофайловые GGUF (проба заголовка читает первый
файл, так что у разделённых моделей большая часть тензоров осталась бы скрытой). Размеры обновляются из
`https://huggingface.co/api/models/<repo>?blobs=true`.

## Загрузка удалённого заголовка (P1.2)

`runa fit` отвечает *до* скачивания, поэтому заголовок GGUF (magic +
метаданные + таблица информации о тензорах) загружается HTTP-запросами `Range`, которые
растут, пока [`Reader::parse`](../../crates/runa-fit/src/gguf.rs) не завершится успешно.
Реализация: `crates/runa-fit/src/remote.rs` (`Fetcher`).

Ссылки на модели (D3):

| Ссылка | Разрешение |
|-----|------------|
| `hf:<repo>:<file.gguf>` | `https://huggingface.co/<repo>/resolve/main/<file.gguf>` |
| `hf:<repo>:<quant>` | список соседних файлов через Hub API → лучшее совпадение с `<quant>` → как выше |
| `https://…` | прямой URL (сервер должен отдавать диапазоны байтов) |
| `<local path>` | тот же цикл «наращивать, пока не распарсится» по файлу (seek, без сети) |

Сопоставление кванта (`pick_quant`): точное имя файла → суффикс через `-`/`_`
(`…-Q4_K_M.gguf`) → подстрока без учёта регистра; при равенстве побеждает самое короткое
имя, затем лексикографический порядок. Детерминировано; покрыто юнит-тестами.

Цикл загрузки: запрашивается `bytes=have..want-1`, начиная с 8 MiB, с удвоением до
предела 256 MiB. Ошибки парсинга, похожие на обрезку (`Truncated`,
`UnexpectedEof`, `TensorTableTruncated`, `StringTooLong`), означают «загрузить
ещё»; любая другая ошибка парсинга означает, что удалённый файл повреждён. Серверы,
которые игнорируют диапазоны (200 вместо 206), принимаются, только если всё
тело укладывается в бюджет заголовка. Аутентификация: bearer `HF_TOKEN` (редиректам на
подписанные URL S3 она не нужна — reqwest убирает авторизацию при переходе на другой домен).

Кеш: `<cache>/runa/headers/` (`XDG_CACHE_HOME`, `%LOCALAPPDATA%`,
`~/.cache`, иначе временный каталог), по одному файлу на URL плюс JSON-файл рядом
(`total_len`, `etag`). Для повторного использования сервер должен сообщить ту же
общую длину и ETag на однобайтовую пробу.

Измерено 2026-09-08 (вживую, холодный старт):

| Модель | Байты заголовка | Тензоры | Размер файла | Время |
|-------|--------------|---------|-----------|---------|
| `hf:unsloth/Qwen3-8B-GGUF:Q4_K_M` | 8 MiB (1 запрос туда-обратно) | 399 | 5.0 GiB | 4.3 s |
| локальный `qwen2-0_5b-instruct-q4_0.gguf` (тестовый сервер) | 8 MiB (1 запрос туда-обратно) | 290 | 353 MiB | 0.2 s |

Холодная загрузка за 4.3 s — это TLS + цепочка редиректов + передача 8 MiB; тёплые
(закешированные) загрузки делают одну однобайтовую пробу. Целевое значение плана `< 3 s`
относится к пути через CLI `runa fit` (P1.11) с тёплым соединением.

## Размещение (P1.8)

`plan_placement` (`crates/runa-fit/src/planner.rs`) максимизирует объём весов, размещённых на GPU,
в пределах `VRAM − margin` (запас по умолчанию 1 GiB, позже — `--fit-margin`).
Вычислительный буфер + KV + mmproj + LoRA-адаптеры резервируются на GPU в первую очередь;
оставшийся бюджет весов заполняется с конца к началу по приоритету вытеснения:
эксперты MoE (`ffn_*_exps`) выгружаются первыми, затем таблицы эмбеддингов/выхода, плотные
attention/FFN — последними. `mmproj_bytes` (по умолчанию 0, задаётся для VL/аудио-моделей —
см. P4.8) и `lora_bytes` (по умолчанию 0, сумма размеров файлов адаптеров `--lora`
— см. P8.5) участвуют в резервировании и в таблице байтов по устройствам
(`gpu_weight_bytes`, `cpu_weight_bytes`, `compute_buffer_bytes`,
`kv_bytes`, `mmproj_bytes`, `lora_bytes`, `gpu_total_bytes`).

Проверено на реальном заголовке Qwen3-30B-A3B: при 8 GiB VRAM эксперты остаются на
CPU, а плотные слои — на GPU; при достаточной VRAM все слои попадают на GPU.
(`real_moe_fixture_small_vram_parks_experts_on_cpu`).

## Контекст медиа / VL (P4.8)

`FitConfig.media` (`MediaFit`) добавляет токены изображений/видео/аудио в проверку
контекста:

```text
media_tokens = frames × tokens_per_frame
             + ceil(audio_seconds) × tokens_per_audio_second
```

По умолчанию: 256 токенов на кадр, 25 токенов на секунду аудио. Если `media_tokens > n_ctx`,
вердикт — `NO FIT` (код выхода 2) с `Warning::MediaExceedsContext`.

VRAM: `PlannerConfig.mmproj_bytes` резервируется на GPU (так же, как compute/KV).
`--draft PATH` (P5.6) добавляет размер draft-файла GGUF к `mmproj_bytes`, чтобы
fit учитывал вторую модель, хотя декодирование всё ещё использует n-gram.
`has_mmproj && mmproj_bytes == 0` по-прежнему выдаёт предупреждение, что размер проектора не
оценён. Рабочая память энкодера — `frames × n_embd × 4 × 8` через
`estimate_encoder_compute`, и она добавляется к резерву на GPU.

## Ограничения NPU (P9.4, Tier 3)

Поддержка NPU — это включаемая по желанию заготовка, а не выгрузка вычислений: у `llama-cpp-2` нет
бэкендов `hexagon`/`openvino` вплоть до 0.1.154 (обзор в
`docs/versions.md`), поэтому каждая оценка NPU ниже — консервативная заглушка,
а размещение всегда остаётся на CPU/GPU. `runa doctor` сообщает
`hexagon-stub` / `openvino-stub`, только если сборка сделана с соответствующей фичей
cargo; `RUNA_NPU=hexagon|openvino` включает в строке вердикта `runa auto`
упоминание результата пробы (без этой переменной вердикт никогда
не упоминает NPU); `RUNA_FAKE_NPU=1|hexagon|openvino` имитирует наличие NPU для
тестов, `RUNA_FAKE_NPU=0` принудительно задаёт отсутствие.

- `HwSpec::hexagon()` — 60 GB/s, 45 TOPS, эффективность 0.30 (NPU класса Snapdragon
  X, без калибровки). Ядра Hexagon DSP подкачивают веса через окно
  ~3.5 GiB: любую модель (или выгруженный срез) больше ~3.5 GiB считайте
  разбитой по окну, а не одним резидентным блоком.
- `HwSpec::openvino()` — 40 GB/s, 13 TOPS (младшая модель), эффективность 0.30
  (без калибровки). Только текстовые модели: пути энкодеров зрения/аудио не проходили
  валидацию на OpenVINO, поэтому мультимодальные оценки делаются только для CPU/GPU.
- Обе заглушки ориентированы на Q4_0: для весов более высокой точности на NPU нет
  измеренной эффективности, поэтому коэффициент 0.30 предполагает кванты класса Q4 и
  занижает прогноз для всего, что крупнее (безопасное направление для вердикта fit).
- Перекалибруйте (`efficiency`, пропускную способность, TOPS) по запускам `runa bench`
  на устройстве, прежде чем называть пользователям скорости NPU; до тех пор вердикт помечает
  их `(uncalibrated Tier-3 estimate)`.
