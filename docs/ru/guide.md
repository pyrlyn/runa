# Руководство пользователя

Примеры флагов и поведения, которые можно копировать. Если не указано иное,
вывод ниже получен при запусках на CPU под macOS с фикстурами из
`tests/fixtures/`. Справочная документация: `config.md` (каждый ключ),
`fit.md` (формулы), `structured.md` (инструменты/MCP), `media.md`
(аудио/зрение), `thinking.md`, `memory.md` (публичный API).

## Калиброванные прогнозы скорости (`runa bench`, `runa fit`)

**Что.** Прогнозы декодирования/префилла масштабируются по истории измерений:
после того как запуск `runa bench` записан, последующие прогнозы для той же
комбинации `(device, backend, quant)` умножаются на медиану отношения измеренное/прогнозное.

**Зачем.** Ошибки некалиброванной модели доходили до 265% на CPU (M3). Три
калибровочных запуска на вашем устройстве сводят типичные ошибки в диапазон
±15%.

**Как.** Каждый `runa bench` дописывает результат в `~/.runa/calibration.json`
(если не указан `--no-calibrate`); `RUNA_CALIBRATION` задаёт другое место.
`bench`, `fit` и `fit --recommend` читают эту базу; пустая или
отсутствующая база оставляет сырой вывод модели нетронутым, а один плохой замер
(нулевой коэффициент или NaN) игнорируется по каждой оси отдельно.

```sh
runa bench qwen2.gguf --mode cpu --pp 512 --tg 128   # записывает замер
runa fit qwen2.gguf --json                            # прогнозы теперь откалиброваны
```

Подтверждено e2e-тестом `fit_calibration_db_scales_predictions`: замер с отношением
измеренное/прогнозное 2.0× ровно удваивает выводимую скорость декодирования.

## Рабочие потоки (`--threads`)

**Что.** `--threads N` для `run` / `chat` / `bench` / `serve`;
`RUNA_THREADS`; `[defaults] threads` в `runa.toml`. Приоритет:
флаг > переменная окружения > файл > встроенное значение по умолчанию.

**Зачем.** Старое значение по умолчанию (все логические CPU, включая E-ядра) проигрывало
автоматическому выбору потоков в `llama-bench` (M4, 27%). Встроенное значение по умолчанию теперь
совпадает с llama.cpp: P-ядра на Apple Silicon
(`hw.perflevel0.logicalcpu`), логические CPU на остальных платформах.

```sh
runa run model.gguf "hi" --threads 4
# это видно в строке вердикта:
# runa load ... threads 4 mmap:true mlock:false
```

```toml
# runa.toml
[defaults]
threads = 8
```

`--threads 0` (или некорректные `RUNA_THREADS` / `[defaults] threads`)
приводит к ошибке ещё до загрузки. Только для GGUF: `--backend mistral` явно
отклоняет этот флаг, а `run --threads …` обходит демон (флаг, влияющий на
загрузку, как и `--device`).

## Язык транскрибации речи (`--lang auto`)

**Что.** `runa media transcribe --lang auto` (по умолчанию)
определяет язык и транскрибирует за один проход.

**Зачем.** Раньше язык определялся правильно, но транскрипт возвращался пустым
(блокер M7): флаг `detect_language` в whisper.cpp означает
*только определить и вернуться без декодирования*. Теперь auto передаёт язык
`"auto"`, не выставляя этот флаг.

```sh
runa media transcribe --model base --lang auto clip.wav
# language: en
# (transcript…)
```

Проверено вживую: вывод с `--lang auto` побайтно совпадает с
выводом `--lang en` на том же аудио.

## Подсчёт токенов рассуждения (`--json`, serve, `/usage`)

**Что.** Каждая генерация подсчитывает токены тела рассуждения
(`Usage.reasoning_tokens`), так что соблюдение бюджета (M6) можно проверить
снаружи:

```sh
runa run qwen3-8b.gguf "What is 2+2?" --think-budget 32 --max-tokens 48 --json
```

```json
{"text":"\n\n2 + 2 equals 4. Here's","usage":{"prompt_tokens":15,"generated_tokens":48,"reasoning_tokens":35,"pp_toks_per_s":77.1,"tg_toks_per_s":15.5},"stop":"max_tokens"}
```

35 ≤ 32 бюджет + grace — ограничение соблюдается *и* отражается в отчёте. Serve показывает
такую же разбивку для chat completions без стриминга:

```json
"usage": {
    "prompt_tokens": 9, "completion_tokens": 4, "total_tokens": 13,
    "completion_tokens_details": {"reasoning_tokens": 0}
}
```

Команда чата `/usage` добавляет `(reasoning N)`, когда N > 0. Бэкенды Mistral и облачные
сообщают 0 (там нет разбивки на рассуждение).

## Сжатие в простое в `serve` / `daemon` (M11)

**Что.** После `idle_timeout_s` (по умолчанию 300, `[memory]`,
`RUNA_MEMORY_IDLE_TIMEOUT_S`) без запросов загруженные движки получают
задание простоя: отображение промпт-кеша LMDB снимается, а модель остаётся
загруженной:

```text
serve: idle qwen2-0_5b-instruct-q4_0: prompt cache released (model kept)
```

**Зачем / ограничения.** Простаивающие CLI и серверы не должны держать отображения
кеша. Измерено: RSS 772.9 MiB до *и* после на модели 0.5B
— освобождение реальное, но ничтожное по сравнению с резидентными
весами, поэтому порог M11 (RSS ≤ floor + 10%) остаётся недостижимым
без выгрузки модели, которую дизайн запрещает. Таймер простоя сбрасывают только
эндпоинты генерации (`chat/completions`, `messages`, `embeddings`,
`transcriptions`); опросы `/health` и `/v1/models` намеренно
этого не делают.

## Стриминговые вызовы инструментов Anthropic (клиент)

**Что.** Клиент на `reqwest`+SSE собирает потоковые блоки `tool_use`
(`content_block_start` + фрагменты `input_json_delta`) в
то же событие `ToolUse`, которое даёт ответ без стриминга, до
`Done`, поэтому цикл инструментов CLI обрабатывает оба пути одинаково.

**Почему стриминг не используется по умолчанию.** Только ответы целым сообщением сохраняют
подписи рассуждения для следующего раунда инструментов; потоковые блоки рассуждения
не несут подписей, которые можно было бы отправить обратно. Поэтому CLI использует вызовы
без стриминга, а путь SSE остаётся корректным запасным вариантом.

## Офлайн-рекомендации с учётом KV и вычислений

**Что.** `runa fit --recommend --offline` проверяет размеры файлов из каталога
без сети — теперь с учётом KV-кеша (линейно по `--ctx`,
`--kv q8_0` вдвое / `q4_0` вчетверо меньше значения для f16) и
вычислительного буфера (линейно по ubatch), а не только весов:

```sh
runa fit --recommend --offline --top 5
# runa fit --recommend · VRAM 12 GiB (RUNA_FAKE_VRAM) · RAM 16 GiB · ctx 8192 · kv f16 · offline: sizes only
#  1. gpt-oss 20B                tier 4    ~11 tok/s  FITS CPU
#     runa pull hf:ggml-org/gpt-oss-20b-GGUF:gpt-oss-20b-MXFP4.gguf
#  2. Qwen2.5 VL 7B Instruct     tier 3    ~98 tok/s  FITS GPU
#     ...
```

Длинный контекст на большой модели больше не «помещается» офлайн, при этом
не помещаясь онлайн. `~` обозначает оценки по размеру.

## Кавычки для серверов MCP (`--mcp`)

**Что.** `--mcp '<command args>'` разбивается по правилам кавычек оболочки:
`'...'` берётся буквально, `"..."` допускает экранирование обратной косой чертой, обратная косая черта
вне кавычек экранирует следующий символ:

```sh
runa run qwen3 "hi" --mcp "python3 'my dir/s.py' --root /tmp"
```

Незакрытые кавычки — ошибка. Всё более сложное (переменные окружения)
задаётся в `[mcp.servers]` (`docs/config.md`).

## История чата между ходами

**Что.** `runa chat` (REPL и `--tui`) отправляет весь транскрипт на данный
момент с каждым ходом, включая раунды инструментов:

```text
> My name is Ada.
Hello! How can I assist you today?
> What is my name? Answer with the name only.
Ada
```

История обрезается целыми ходами, начиная с самых старых, при превышении ~75% от `--ctx`, с
уведомлением `(history trimmed to fit ctx)`. При локальной загрузке считаются реальные токены
через собственный токенизатор модели; через сокет демона (токенизатора там
нет) обрезка откатывается к оценке «символы/4» — это в любом случае страховочное
ограждение, поскольку движок всё равно громко падает при превышении реального ctx.
`/reset` и `/model` очищают историю (`/mode` сохраняет её: веса те же).
Неудачные ходы ничего не записывают, поэтому повтор отправляет ту же историю.

## Записи каталога для split-GGUF

**Что.** Запись каталога может перечислять ссылки на шарды 2..N в `parts`
(`ref` остаётся частью 1); проба суммирует байты тензоров по заголовкам
всех частей перед проверкой. Тогда `size` — это сумма байтов частей:

```toml
[[model]]
name = "Example 70B split"
ref = "hf:org/model:model-00001-of-00003.gguf"
parts = ["hf:org/model:model-00002-of-00003.gguf",
         "hf:org/model:model-00003-of-00003.gguf"]
size = 42520398432
```

Пока ни одной разделённой записи не поставляется (всё, что есть в каталоге, помещается в один
файл); поддержка схемы и пробы покрыта тестами и ждёт
первой шардированной модели, которая поместится на оборудование Tier-1/2.

## Вызовы инструментов Harmony (gpt-oss)

**Что.** Запросы с инструментами формируются через собственный шаблон модели,
поэтому gpt-oss говорит на Harmony (`<|channel|>commentary
to=functions.…`), Qwen3 — на Hermes `<tool_call>`, а
модели без шаблона откатываются к обобщённому JSON. Покрыто тестами на
реальном шаблоне 20B при обоих порядках заголовков; шаблоны с `thinking_forced_open`
не требуют особой обработки на клиенте (llama.cpp сам управляет флагом
на основе нашего `enable_thinking` — подтверждено тем, что обязательный вызов инструмента Qwen3-8B
завершается в пределах бюджета рассуждения 64+8).

## Ограничение нагрузки на систему (`--max-load-percent`)

**Что.** Ограничение только с предупреждениями (по умолчанию 80%) на долю общих
ресурсов системы, которую может использовать запуск: `--max-load-percent N` для `run` /
`chat` / `bench` / `serve` / `daemon`, `RUNA_MAX_LOAD_PERCENT`,
`[system] max_load_percent`. Приоритет: флаг > переменная окружения > файл.

**Зачем.** Предупреждение заранее, прежде чем большая модель придавит машину: каждое
превышение выводит практичное `warning:` с указанием значения, которое нужно задать.
Запуск всегда продолжается — это никогда не фатально.

```sh
runa run model.gguf "hi" --threads 16
# warning: system already uses ~924 MiB RAM (91% of 1024 MiB), above
#   max_load_percent=80 — set max_load_percent to at least 91 (...)
# warning: --threads 16 wants ~100% of 16 CPUs, above
#   max_load_percent=80 — set max_load_percent to at least 100 (...)
#   or lower --threads to 12
```

Предусмотрено три строки: потребность модели в RAM (после чтения заголовка),
фоновое давление на RAM и доля CPU для `--threads`. Значения вне диапазона
приводят к ошибке до загрузки. С этим флагом `run` не использует демон
(демон не знает ограничений для отдельного запроса), а с
`--backend mistral` флаг отклоняется (там предупреждений не бывает).

## Адрес привязки serve и `--api-key`

**Что.** `runa serve` по умолчанию слушает `127.0.0.1`. Не-loopback
`--host` (`0.0.0.0`, `::`, адрес в локальной сети, имя хоста) отклоняется,
если не задан `--api-key`. Loopback — это `127.0.0.0/8` и `::1`
(включая `[::1]` и IPv4-mapped `::ffff:127.0.0.1`).

**Зачем.** `/v1` отдаёт completions, embeddings и transcriptions.
Привязка ко всем интерфейсам без ключа открывает этот API в сеть.
`/health` остаётся открытым, чтобы проверка могла увидеть, жив ли процесс.

**Как.** С ключом каждый маршрут `/v1` требует
`Authorization: Bearer <key>`. Отсутствующий или неверный токен — это HTTP 401
`invalid api key`. Тот же флаг закрывает и loopback-привязку. Ключа
в `runa.toml` для этого токена нет.

```sh
runa serve model.gguf --port 8080
runa serve model.gguf --host 0.0.0.0 --api-key "$SERVE_KEY"
curl -H "Authorization: Bearer $SERVE_KEY" http://127.0.0.1:8080/v1/models
```
