# docs/profiles.md — профилирование и полиглотная оценка (K3, K4, P5.1)

## K3 — оценка полиглотного «запасного выхода» (D19, критерий D1)

**Кандидат:** предобработка изображений `resize` + `normalize` + `patchify` (P5.4) через
`fast_image_resize` (Rust, чистый) против C `stb_image_resize` (один заголовочный файл, `cc`).

**Интерфейс:** `runa-media::image::resize()` принадлежит Rust (`ImageBuf` → `ImageBuf`);
путь на C был бы в `runa-media/src/image_c.c` под `#[cfg(feature = "c-resize")]`
с идентичным `ImageBuf` на входе/выходе и диспетчеризацией через `#[cfg]`.

**Бенчмарк (M3 Max, 512×512 RGB → 336×336, 100 итераций, `criterion`):**

| Реализация | среднее | ± | против Rust |
|------|------|---|---------|
| Rust `fast_image_resize` (по умолчанию) | 1.82 ms | 0.04 | — |
| C `stb_image_resize` (`cc -O3`) | 1.79 ms | 0.05 | **+1.7%** |

*Эквивалентность:* `cargo test -p runa-media --test image` попиксельно `max_diff ≤ 1` (u8) на
`tests/fixtures/shapes.png` и 10 синтетических градиентах.

**Критерий D1:** C должен обгонять Rust на **≥5% сквозь весь конвейер или в ≥2× на изолированной операции**.
Результат **+1.7%** критерию **не** соответствует.

**Решение:** **REJECT** — оставить путь на Rust. `image_c.c` не влит; интерфейс Rust
остаётся. Переоценивать при каждом обновлении тулчейна (D19).

**Другие рассмотренные кандидаты (бенчмарков пока нет):**
- Ресемплинг аудио: `rubato` (Rust) против `libsamplerate` (C): `rubato` уже
  в 2–3× быстрее `libsamplerate` на x86_64 в ранних спайках P4.1; путь на C не нужен.
- Whisper: `sherpa-onnx` (Rust-биндинг над C++ ONNX) против `whisper-rs` (C): Parakeet —
  полиглотный кандидат с наибольшей отдачей для P4.2, но ему нужны C++-рантайм `sherpa-onnx`
  и скачивание модели (25 языков). Оценка отложена до P4.2.

## K4 — аудит параллелизма (D20)

**Аудит 2026-09-08 (M3 Max, 4 ядра, `moon run :test` против `cargo test --workspace`):**

| Путь | До | После | Время по часам | Решение |
|------|--------|-------|-----------|----------|
| `cargo test --workspace` (8 крейтов, последовательно) | `cargo test -p runa-fit && cargo test -p runa ...` | `moon run :test` (параллельно, с кешем, 4 ядра) | 12.3s → 6.1s (2.0×) | Оставить moon; источником истины остаётся cargo |
| `runa doctor --bench` (memcpy на CPU, 64 MiB) | однопоточный `copy_from_slice` | `rayon`, 4 куска `par_chunks_mut` | 0.04s → 0.02s (2×) | Оставить rayon; критерий D1 выполнен |
| `runa-fit::Fetcher::fetch_header` | синхронный `reqwest::blocking` (текущий) | `reqwest::async` + `tokio` | выигрыша по времени нет (загрузка заголовка упирается в задержку, один диапазон на запрос туда-обратно) | Оставить синхронный (D20: параллелизм, который не сдвигает время по часам, удаляется) |
| декодирование аудио в `runa-media` (10 клипов) | последовательный `symphonia` на каждый файл | `rayon` по файлам | 1.2s → 0.7s (1.7×, 4 ядра) | Пока оставить последовательно (критерий 2× не выполнен); переоценить на 32 клипах |

*Не осталось ни одного последовательного горячего пути без обоснования бенчмарком. Работа, упирающаяся в I/O, остаётся синхронной там, где async не помогает; работа, упирающаяся в CPU, распараллелена по данным там, где измерено ≥1.5×.*

Таблица аудита хранится здесь согласно проверке K4; время по часам `moon run :test` против `cargo test` записано выше.

## P5.1 — обвязка для профилирования (топ-10 операций по режимам)

**Инструменты (локально + ночной P5.8):**

| Инструмент | Установка | Команда |
|------|---------|---------|
| `samply` | `cargo install samply` | `samply record cargo run -p runa-engine --example gen -- tests/fixtures/qwen2-0_5b-instruct-q4_0.gguf "hi"` |
| `cargo flamegraph` | `cargo install flamegraph` | `cargo flamegraph -p runa -- bench tests/fixtures/qwen2-0_5b-instruct-q4_0.gguf` |
| `criterion` (ядра) | dev-зависимость в `runa-kernels` | `cargo bench -p runa-kernels --bench softmax` |

**Порядок действий:** профилируйте pp512 (префилл) и tg128 (декодирование) по отдельности через `runa bench --json`;
для внутренностей ggml используйте `samply` на примере `gen` или `runa bench` с включёнными Metal/CUDA.
Запишите в этот файл топ-10 символов по числу сэмплов для каждого режима.

**Первый спайк (M3 Max Metal, пример `gen`, qwen2-0.5B Q4_0):** в декодировании доминируют
ядра `ggml_metal` (`kernel_mul_mv_q4_0`, `kernel_flash_attn`); сэмплирование на Rust занимает <1%
времени по часам на tokens/sec — это согласуется с порядком D14 (ядро сэмплирования — P5.3, пока не горячее).

**Колбэки планировщика ggml:** не подключены в закреплённой обёртке `llama-cpp-2` 0.1.133;
вернуться к этому, когда обновлённый llama.cpp предоставит стабильные хуки для замера времени по операциям.

| Режим | Машина | Топ операций (% сэмплов) | Примечания |
|------|---------|-------------------|-------|
| декодирование tg128 | M3 Max Metal | `kernel_mul_mv_q4_0` ~45%, `kernel_flash_attn` ~30% | из `samply` на `gen` |
| префилл pp512 | — | ожидается | запустить `runa bench` + samply |
| декодирование на cpu | — | ночной | `.github/workflows/perf.yml` (P5.8; на раннерах GitHub, пока нет self-hosted) |

## P4.9 — профиль медиаконвейера (кандидаты для P5)

**Машина:** M3 Max, `cargo bench -p runa-media --bench media` (release, criterion, 20 сэмплов).
**Воспроизведение:** та же команда; HTML в `target/criterion/`.
**Flame:** [profiles-p49.svg](../profiles-p49.svg) — собственное время Rust для клипа 5 s (32 VL-кадра + 5 s аудио 48 kHz с ресемплингом до 16 kHz). `samply` / `cargo flamegraph` не было в PATH; SVG построен по средним значениям criterion ниже, а не по сэмплированному стеку.

| Операция | Размер | среднее | клип 32 кадра / 5 s |
|----|------|------|---------------------|
| `resize_rgb` nearest 512→336 | один кадр | **73 µs** | 2.3 ms |
| `normalize_rgb` → [−1, 1] | 336² RGB | **42 µs** | 1.3 ms |
| `histogram_l1` (смена сцены) | пара 336² | **642 µs** | **20.5 ms** |
| `resample_mono` rubato 48 k→16 k | 1 s PCM | **1.38 ms** | 6.9 ms |

**Mel:** в `runa-media` не реализован. Whisper.cpp (`whisper-rs` 0.16) строит log-mel внутри C++-рантайма после того, как мы передаём ему PCM 16 kHz. Ядро mel на Rust/C окупилось бы, только если мы уйдём от whisper; в списке P5 этого нет.

**Ранжирование для P5 (критерий ≥5% e2e или ≥2× изолированно):**

1. **`histogram_l1`** — ~65% этого Rust-среза, 9× от ресайза. Лучший изолированный кандидат на ядро (гистограмма на NEON/AVX). **Не** сдвигает e2e для VL/ASR (доминируют ffmpeg + whisper). Отложить, если только определение сцен не проявится в полном samply для `runa media video`.
2. **`resize_rgb`** — nearest уже 73 µs; высококачественный `fast_image_resize` в K3 занимал **1.82 ms** (в 25× медленнее). P5.4 — это замена ради качества, а не выигрыш в скорости по сравнению с nearest.
3. **`normalize_rgb`** — 42 µs скалярно; NEON SIMD 26.8 µs (**1.52×**, P5.4). Критерий D14 — 2× → REJECT, оставить скалярную версию.
4. **`resample_mono`** — K3 уже отверг `libsamplerate`; rubato остаётся.
5. **whisper mel** — живёт в ggml/whisper.cpp; это не задача для `runa-kernels`, если только мы не заменим ASR.

**ffmpeg / whisper** (не входят в бенчмарк, порядок величин по P4.1/P4.2/P4.5): декодирование + ASR для 5 s аудио занимают от сотен ms до секунд. Таблица предобработки на Rust — несколько десятков ms. Время на P5 стоит тратить на сэмплирование ggml (P5.3) и, если вообще, на гистограмму сцен — а не на resize/normalize/mel в этом крейте.
