## Соответствие llama-cpp-2 → llama.cpp (проверенная цепочка)

1. `llama-cpp-2 0.1.133` опубликован 2026-02-03 из
   тега `0.1.133` репозитория `utilityai/llama-cpp-rs` = коммит `349ae33`
   (`.cargo_vcs_info.json` крейта).
2. Дерево репозитория на этом коммите закрепляет сабмодуль
   `llama-cpp-sys-2/llama.cpp` на `1051ecd28907d2ca0a15c135f190fe415d0a3d1b`.
3. Этот коммит — ровно релизный тег llama.cpp **`b7709`** (2026-01-12,
   "vulkan: Disable large coopmat matmul configuration on proprietary AMD
   driver", #18763). Перекрёстная проверка: тег `b8400` опережает его на 691 коммит, и
   8400 − 7709 = 691 — номера тегов llama.cpp считают коммиты, так что соответствие
   точное.
4. `llama-cpp-2 0.1.133` зависит от `llama-cpp-sys-2 ^0.1.133` (фичи
   пробрасываются); на macOS arm64 крейт автоматически включает `metal` через sys-
   крейт.

Флаги фич, доступные в 0.1.133: `cuda`, `cuda-no-vmm`, `metal`,
`vulkan`, `openmp`, `mtmd`, `sampler`, `dynamic-link`, `system-ggml`,
`android-shared-stdcxx`.

> **Отклонение от плана D2:** фичи `native` (указана в D2, используется в
> P5.7) **нет в llama-cpp-2 0.1.133**. Она появляется в более поздних
> релизах llama-cpp-2 (есть к 0.1.156). Переносимые релизные сборки должны
> полагаться на диспетчеризацию ggml во время выполнения (D13), пока мы не обновимся дальше этого пина;
> диспетчеризацию `runa-kernels` (P5.2) это не затрагивает.

### Обзор пинов для NPU (P9.4, 2026-09-15)

Вопрос: предоставляет ли какой-нибудь более новый `llama-cpp-2` фичи cargo `hexagon`/`openvino`
для среза NPU в P9.4?

- Проверен `llama-cpp-2` **0.1.154** (тарбол крейта
  `llama-cpp-2-0.1.154.crate`, git `bed81ad4`, плюс страница фич на docs.rs):
  полный список фич — `android-shared-stdcxx`,
  `android-static-stdcxx`, `common`, `cuda`, `cuda-no-vmm`, `default`,
  `dynamic-backends`, `dynamic-link`, `llguidance`, `metal`, `mkl`,
  `mtmd`, `opencl`, `openmp`, `rocm`, `sampler`, `static-openmp`,
  `static-stdcxx`, `system-ggml`, `system-ggml-static`, `vulkan`.
  **Ни `hexagon`, ни `openvino`.** (0.1.154 добавляет `opencl`, `rocm`, `mkl`,
  `llguidance`, `dynamic-backends` по сравнению с нашим пином 0.1.133; ни одна из них не является путём
  для NPU.) Соответствующая страница docs.rs для `llama-cpp-sys-2` 0.1.154 показывает
  тот же набор.
- Локально проверено, что ссылка на несуществующую фичу зависимости
  (`hexagon = ["llama-cpp-2/hexagon"]`) ломает **даже разрешение по умолчанию**
  (`cargo build` падает на этапе разрешения), поэтому фичи P9.4
  не могут пробрасываться в llama-cpp-2, пока upstream их не добавит.

Решение: **ждать** (оставить пин `=0.1.133`; P9.4 поставляет только пробу +
ограничения сборки + документацию):

- `system-ggml` / `system-ggml-static` увели бы сборку с закреплённого
  llama.cpp (b7709) на тот ggml, который предоставляет хост, — это ломает дисциплину пинов D16
  и воспроизводимость сборки ради пути Tier-3.
- `dynamic-backends` загружает только бэкенды ggml, встроенные в тот же закреплённый
  llama.cpp на этапе компиляции; он не может сотворить бэкенды Hexagon/OpenVINO,
  без которых пин был собран.
- Запасной вариант D2 с `bindgen` (собственные биндинги поверх `llama.h`)
  несоразмерен для оборудования Tier-3/ручной проверки без CI-раннеров.

Что разблокирует реальную выгрузку на NPU, по порядку: (1) фичи `hexagon`/`openvino`
в upstream `llama-cpp-2` (или релиз ggml с этими бэкендами, ради которого стоит
сознательно обновить пин через критерии D1/D15); (2) SDK вендоров
(`HEXAGON_SDK_ROOT`, `INTEL_OPENVINO_DIR`); (3) ручная валидация на устройстве
+ калибровка заглушек `HwSpec::{hexagon,openvino}` и маркеров
`npu_present()`. До тех пор фичи cargo `hexagon`/`openvino`
— заглушки только для пробы: их включение никак не меняет размещение (тензоры
остаются на CPU — план D12).

## Флаги сборки (P5.7)

| Сборка | Флаги | Примечания |
|-------|-------|-------|
| Локальная разработка (macOS arm64) | `cargo build -p runa-engine --features metal` | На Apple Silicon Metal включён по умолчанию через `llama-cpp-sys-2` |
| Локальная разработка (Linux CUDA) | `--features cuda` для `runa-engine` / воркспейса | Задача CI на ubuntu — только CPU; CUDA в остальных местах только собирается |
| Переносимый релиз | без `-march=native`; диспетчеризация ggml во время выполнения (D13) | `native` в `llama-cpp-2` появляется после пина 0.1.133 — перед включением перейдите на более новый пин |
| `runa-kernels` (P5.2+) | для новых ядер предпочтителен Zig (C ABI) (D23); C/`.S` только там, где Zig хуже | SIMD через Zig `@Vector` или диспетчеризацию на C во время выполнения |

Релизные бинарники должны работать на хостах **без** AVX-512; не поставляйте `-C target-cpu=native` в релизных профилях (в `[profile.release]` файла `Cargo.toml` нет `target-cpu`).

Важные для runa особенности релиза 0.1.133: биндинги mtmd
(аудио/изображения/видео через `LlamaContext`/контекст mtmd), вызов функций +
вспомогательные функции конвертации в стиле OpenAI, цепочка сэмплеров. Обратите внимание, что llama.cpp позже удалил
свой OpenAI-совместимый сервер в upstream (синхронизация llama-cpp-2 0.1.147) —
для нас это неважно: `runa serve` — наш собственный сервер на axum (D11).

### Бэкенд RPC: вендоренный, за фичей (P9.3, 2026-09-15)

llama.cpp b7709 поддерживает распределённый инференс через бэкенд RPC
(`--rpc host:port`, `ggml_backend_rpc_add_server`), и ни один опубликованный
`llama-cpp-2` (просмотрены 0.1.131–0.1.156 через sparse-индекс — ни один не предоставляет
фичу `rpc`) не может его собрать, но ни форк, ни повышение пина не понадобились.
Опубликованный крейт `llama-cpp-sys-2 0.1.133` содержит все заголовки, нужные бэкенду
(`ggml-rpc.h`, плюс внутренние `ggml-impl.h`,
`ggml-backend-impl.h`, `ggml-common.h`); вырезан только каталог реализации `ggml-rpc/`
размером 78 KB, поэтому `-DGGML_RPC=ON` падает на этапе конфигурации CMake
(`add_subdirectory(ggml-rpc)` → отсутствующий каталог), а
`wrapper.h` никогда не разбирает `ggml-rpc.h` (нет биндингов `ggml_backend_rpc_*`).
`GGML_USE_RPC` в ядре ggml лишь автоматически регистрирует *пустую* базовую регистрацию —
реальный поток (`ggml_backend_rpc_add_server` → `ggml_backend_register`) идёт
через публичный C API, поэтому `runa-engine` компилирует дословный `ggml-rpc.cpp` из b7709
(вендорен в `crates/runa-engine/rpc/` с побайтно идентичными
заголовками, см. `rpc/README.md`) в `build.rs` за новой фичей cargo `rpc`
(C++17, `ws2_32` в Windows) и регистрирует каждый эндпоинт `--rpc` в `load()`
до инициализации бэкенда — так же, как `common/arg.cpp:add_rpc_devices` в upstream.
Прослойка в стиле `#[link]` не понадобилась: символы берутся из нашего собственного
скомпилированного объекта, совместимого по ABI с теми же исходниками b7709, которые собирает sys-крейт.
Защита пина в `build.rs` прерывает сборку с `rpc`, если `llama-cpp-sys-2` уходит
от `=0.1.133` (D16; правило обновления в `rpc/README.md`).

Использование: `runa run --rpc 192.168.1.5:50052 --device RPC0 model.gguf`
(`--rpc` только регистрирует; удалённые устройства перечисляются как `RPC0`, `RPC1`, …
и выбираются явно через `--device` — никогда неявно, D12).
`runa doctor` сообщает `rpc: true/false`; `runa fit --rpc` оценивает
локальное размещение с явным примечанием. Протестировано через loopback с фейковым TCP-
сервером, отвечающим на `HELLO` 3.6.0 + `DEVICE_COUNT` (`runa-engine/tests/rpc.rs`).

### Обзор обновления движка: `llama-cpp-2` 0.1.156 (2026-09-15, вердикт: WAIT)

Повышение `=0.1.133` → `=0.1.156` было предпринято и **откачено**. Пять ошибок
компиляции, все в пути структурированного вывода / вызова инструментов (P8.1/P8.2):
upstream удалил весь слой oaicompat, на котором построены эти возможности
(`apply_chat_template_oaicompat`, `OpenAIChatTemplateParams`,
`ChatTemplateResult`, `GrammarTrigger*`, `wrapper_oai.*`). Его замена
(`common/chat.{h,cpp}` + парсеры peg/auto, собираемые по умолчанию через новую
фичу cargo `common`) — это API с типами C++ (`std::string`, `std::vector`,
`nlohmann::ordered_json`) без биндингов для Rust; восстановить на нём P8.1/P8.2
значит написать прослойку на C и полностью перепроверить грамматики, ленивые/жадные триггеры
и полные циклы инструментов в обоих SDK. Согласно плану D16 (сознательные обновления движка
через критерий бенчмарков) пин остаётся на `=0.1.133`, пока этот перенос не
будет запланирован как отдельная задача; вендоринг RPC выше (протокол 3.6.0) остаётся
согласованным с b7709. Учтите, что будущее повышение также переведёт протокол RPC на 5.0.0
(сабмодуль `e79e4bf`) — обновите `rpc/` вместе с ним.

## Соответствие whisper-rs → whisper.cpp (проверенная цепочка)

1. `whisper-rs 0.16.0` (последний, 2026-03-12, codeberg `tazz4843/whisper-rs`,
   коммит `7558e1b7`) требует `whisper-rs-sys ^0.15`; единственный 0.15.x —
   0.15.0, опубликованный в тот же день из того же коммита.
2. sys-крейт поставляет whisper.cpp как сабмодуль `sys/whisper.cpp`,
   закреплённый на `2eeeba56e9edd762b4b38467bab96c2517163158`.
3. Этот коммит — whisper.cpp **`v1.8.3`**, буквально коммит повышения версии
   `release : v1.8.3` (2026-01-15, CMake 1.8.2 → 1.8.3).

Флаги фич в 0.16.0: `cuda`, `hipblas`, `metal`, `vulkan`, `openblas`,
`raw-api`, `log_backend`, `tracing_backend`.

Upstream whisper.cpp ушёл вперёд (v1.8.4 … v1.8.7, затем v1.9.x; последний
просмотренный: **v1.9.3**, 2026-09-08). Поэтому наш пин ASR отстаёт примерно на 2 минорные
линейки; обновляйтесь через критерий бенчмарка M7 (1 минута речи < 5 s на CPU),
когда whisper-rs перейдёт на более новый whisper.cpp.

## mistral.rs

0.8.1 (2026-04-02), MIT, MSRV 1.88. Фасад `mistralrs` реэкспортирует
билдеры и типы `mistralrs-core 0.8.x`; runa использует высокоуровневый
`ModelBuilder` (с автоопределением, умеет работать с локальным каталогом) плюс
`blocking::BlockingModel` / `BlockingStream` (собственный рантайм tokio, синхронный итератор

0.8.1 нет, поэтому `default-features = false` — пустой пин на будущее;
ускорение на GPU (`metal`, `cuda`, …) остаётся включаемым по желанию согласно D13 и пока не пробрасывается
(бэкенд сам сопоставляет устройства). Обновляйтесь на линейку 0.9.x, если/когда она
выйдет; учтите, что текст плана/дорожной карты, ожидавший `0.9.3`, был написан
до того, как эта версия появилась в upstream (последняя на crates.io на момент
написания — 0.8.1).

## Нативная и переносимая сборки (P5.7)

**Релизные** сборки по умолчанию переносимы: `llama-cpp-sys-2` выставляет `GGML_NATIVE=OFF`,
а ggml во время выполнения выбирает AVX2 / AVX-512 / NEON / SME. Такой бинарник работает на
машине без AVX-512.

Локальные сборки под конкретный хост:

```sh
RUSTFLAGS='-C target-cpu=native' cargo build --release --features native
```

Сам по себе `--features native` **не** передаёт `-march=native` в llama.cpp
(у крейта нет фичи cargo `native`). `llama-cpp-sys-2` включает
`GGML_NATIVE=ON`, только когда видит `-C target-cpu=native` в `RUSTFLAGS`.
`runa-kernels` следует тому же правилу: Zig собирает с `-mcpu=baseline`, а
с `-mcpu=native` — только при `-C target-cpu=native`. `whisper-rs-sys` собирает
собственный ggml, у которого в CMake по умолчанию `GGML_NATIVE=ON`; `.cargo/config.toml`
выставляет `GGML_NATIVE=OFF` (экспортированный `GGML_NATIVE=ON` всё равно побеждает). Иначе
библиотека, собранная на хосте с AVX-512 (закешированная сборка CI, релизный раннер), вызывает
SIGILL на более старом CPU.
`runa doctor --json` сообщает `native_build` (true тогда и только тогда, когда бинарник скомпилирован
с `--features native`) и `backends` (`cpu` плюс любые из `metal` / `cuda` /
`vulkan` / `mtmd`, вкомпилированные в сборку). Тег `vX.Y.Z` запускает `.github/workflows/release.yml`
(архивы cargo-dist 0.33 для CPU + установщики shell/powershell/homebrew). GPU-
варианты: `.github/workflows/release-variants.yml`. Формула Homebrew лежит в
GitHub Release; для `brew install listepo/runa/runa` нужен tap-репозиторий
`listepo/homebrew-runa`. Локально: `bash scripts/cargo-dist.sh generate --mode=ci --check`.

### Пакет ketch (`ketch.toml`)

Корневой `ketch.toml` — это манифест [ketch](https://github.com/listepo/ketch)
для этого репозитория: файл, который `ketch registry push` предлагает в
`listepo/ketch-registry` как `runa/ketch.toml`, и то, что показывает `ketch info runa`,
когда он там окажется. Вывод из `github:listepo/runa` уже работает и без
него; манифест закрепляет выбор ассета.

| Поле | Значение |
|-------|-------|
| `source` | `github:listepo/runa` |
| `bin` | `runa` (корень распакованного архива cargo-dist) |
| `[asset] include` | `*.tar.xz`, `*windows-msvc.zip` |
| `[asset] exclude` | GPU-варианты (`-metal`, `-vulkan`, `-cuda`), установщики shell / powershell / homebrew, `dist-manifest.json`, `*.sha256`, тарбол исходников |

GPU-архивы здесь важны: `release-variants.yml` загружает их под теми же
целевыми тройками, что и переносимые CPU-архивы (`runa-aarch64-apple-darwin`
против `runa-aarch64-apple-darwin-metal`), поэтому без списка `exclude` оценка
ассетов могла бы выбрать вариант, которому нужны вкомпилированные GPU-фичи. Блока
`trust` нет: релиз не публикует файлов подписей рядом с ассетами, и политика `trust`
проваливала бы каждую установку.

Проверяйте изменение до пуша (дерево реестра состоит из каталогов
`<package>/ketch.toml`):

```sh
TMP=$(mktemp -d); mkdir -p "$TMP/runa"; cp ketch.toml "$TMP/runa/"
ketch registry validate "$TMP"    # validated 1 package
```

### Процесс релиза

Релиз — это коммит версии плюс тег, которые создаёт `scripts/release.sh`
(подробности, режимы и список того, что не подключено: [`release.md`](../release.md)). Тег —
это то, что сгенерированный dist `release.yml` превращает в GitHub Release.

## Политика обновлений (D16)

- llama.cpp развивается быстро: ~8–12 тегов в день, и **номера тегов считают коммиты**
  (b7709 → b8400 = 691 коммит). llama-cpp-2 выпускается примерно раз в неделю и не
  следует semver — всегда закрепляйте точно и обновляйтесь сознательно, не чаще раза в месяц.
- Каждое обновление проходит критерий бенчмарков (D1: ядра должны обгонять путь ggml
  на ≥ 5 % сквозь весь конвейер или в ≥ 2× изолированно; D15: perf CI падает при регрессии > 3 %)
  и обновляет `Cargo.lock` и этот файл в том же изменении.
- Последнее, что было просмотрено 2026-09-08: llama-cpp-2 **0.1.156** (llama.cpp ≈ b10405+),
  whisper-rs 0.16.0 (без изменений, но whisper.cpp в upstream уже на v1.9.3),
  async-openai 0.42.0.
