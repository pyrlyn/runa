# Внутрішня будова перевірки вміщення (fit-checker)

Формули, оцінювачі та калібрування для `runa fit` (план P1, рішення
D5/D6). Розділи про оцінювачі з'являються разом зі своїми задачами (P1.5 — обчислювальний буфер,
P1.9 — модель швидкості); цей файл починається з CLI та шляху віддаленого читання
заголовка (P1.2).

## CLI

```sh
runa fit hf:unsloth/Qwen3-8B-GGUF:Q4_K_M --ctx 16384 --kv q8_0
runa fit ./model.gguf --json
runa fit --recommend --use code --top 3
runa fit --recommend --offline
```

`runa fit <model>` приймає локальний GGUF, аліас, `hf:<repo>:<file-or-quant>`
або URL http(s). Завантажена копія читається з диска; для всього іншого завантажується
лише заголовок. Команда друкує звіт із вердиктом (таблиця пам'яті, декодування,
префіл, TTFT, попередження, пропозиції) і завершується з кодом `0` (вміщається), `1` (вміщається з
попередженнями) або `2` (не вміщається). `--json` друкує ті самі числа одним об'єктом.
Сусідній `mmproj-*.gguf` локальної моделі враховується. `--rpc host:port,…`
(P9.3) оцінює лише локальне розміщення: без cargo-функції `rpc`
друкується явне попередження, з нею — примітка, що віддалена пам'ять не
враховується; `runa run --rpc … --device RPC0` звертається до серверів під час завантаження.

`--recommend` паралельно перевіряє вміщення кожної моделі з вбудованого каталогу
(`crates/runa-fit/src/catalog.toml`, `runa_fit::recommend`) і
виводить перші `--top` (типово 5), кожну з посиланням для `runa pull`. Записи з NO FIT
відкидаються. Решта ранжується так:

1. спершу придатна швидкість (прогнозоване декодування ≥ 5 tok/s),
2. потім рівень якості (1 — мала … 4 — найкраща в каталозі),
3. потім прогнозоване декодування в tok/s.

`--use chat|code|vision|reasoning` залишає моделі, позначені для цього сценарію;
з `vision` враховується розмір проєктора. Заголовки кешуються після першого
запуску (див. нижче). `--offline` не потребує мережі: він порівнює розмір файлу з каталогу
(+ проєктор) з VRAM мінус запас, інакше з RAM, і прогнозує
декодування з пропускної здатності над активними байтами (записи MoE їх зберігають). KV
та обчислювальні буфери офлайн не враховуються, а швидкості друкуються з `~`.
Невдала перевірка друкує `skip <name>: <error>` у stderr. Якщо нічого не вміщається,
команда завершується з кодом `2`.

Каталог містить лише однофайлові GGUF (перевірка заголовка читає перший
файл, тож розділені моделі приховали б більшість своїх тензорів). Оновлюйте розміри з
`https://huggingface.co/api/models/<repo>?blobs=true`.

## Віддалене читання заголовка (P1.2)

`runa fit` відповідає *до* завантаження, тож заголовок GGUF (magic +
метадані + таблиця інформації про тензори) завантажується HTTP-запитами `Range`, що
збільшуються, доки [`Reader::parse`](../../crates/runa-fit/src/gguf.rs) не спрацює успішно.
Реалізація: `crates/runa-fit/src/remote.rs` (`Fetcher`).

Посилання на моделі (D3):

| Посилання | Розв'язання |
|-----|------------|
| `hf:<repo>:<file.gguf>` | `https://huggingface.co/<repo>/resolve/main/<file.gguf>` |
| `hf:<repo>:<quant>` | список файлів через Hub API → найкращий збіг із `<quant>` → як вище |
| `https://…` | прямий URL (має віддавати діапазони байтів) |
| `<local path>` | той самий цикл «збільшувати до успішного розбору» над файлом (seek, без мережі) |

Пошук квантизації (`pick_quant`): точна назва файлу → з суфіксом через `-`/`_`
(`…-Q4_K_M.gguf`) → підрядок без урахування регістру; за рівності перемагає найкоротша
назва, потім лексикографічний порядок. Детерміновано; покрито модульними тестами.

Цикл завантаження: запитувати `bytes=have..want-1`, починаючи з 8 MiB і подвоюючи до
межі 256 MiB. Помилки розбору, характерні для обрізаних даних (`Truncated`,
`UnexpectedEof`, `TensorTableTruncated`, `StringTooLong`), означають «завантажити
більше»; будь-яка інша помилка розбору означає, що віддалений файл пошкоджено. Сервери,
що ігнорують діапазони (200 замість 206), приймаються лише тоді, коли все
тіло вміщається в бюджет заголовка. Автентифікація: bearer `HF_TOKEN` (перенаправлення на
підписані URL S3 її не потребують — reqwest прибирає автентифікацію при переході між доменами).

Кеш: `<cache>/runa/headers/` (`XDG_CACHE_HOME`, `%LOCALAPPDATA%`,
`~/.cache`, інакше тимчасовий каталог), один файл на URL плюс супровідний JSON
(`total_len`, `etag`). Для повторного використання сервер має повідомити ту саму
загальну довжину та ETag на перевірці в 1 байт.

Виміряно 2026-09-08 (наживо, без кешу):

| Модель | Байти заголовка | Тензори | Розмір файлу | Час |
|-------|--------------|---------|-----------|---------|
| `hf:unsloth/Qwen3-8B-GGUF:Q4_K_M` | 8 MiB (1 обмін) | 399 | 5.0 GiB | 4.3 s |
| локальний `qwen2-0_5b-instruct-q4_0.gguf` (тестовий сервер) | 8 MiB (1 обмін) | 290 | 353 MiB | 0.2 s |

Холодне завантаження за 4.3 s — це TLS + ланцюжок перенаправлень + передача 8 MiB; теплі
(кешовані) завантаження роблять одну перевірку в 1 байт. Ціль плану `< 3 s` стосується
шляху CLI `runa fit` (P1.11) з теплим з'єднанням.

## Розміщення (P1.8)

`plan_placement` (`crates/runa-fit/src/planner.rs`) максимізує ваги, резидентні на GPU,
у межах `VRAM − margin` (типовий запас 1 GiB, згодом `--fit-margin`).
Обчислювальний буфер + KV + mmproj + LoRA-адаптери резервуються на GPU першими;
решта бюджету для ваг заповнюється з кінця на початок за пріоритетом витіснення:
експерти MoE (`ffn_*_exps`) вивантажуються першими, потім таблиці embedding/output, щільні
attention/FFN — останніми. `mmproj_bytes` (типово 0, задається для VL- та аудіомоделей —
див. P4.8) і `lora_bytes` (типово 0, сума розмірів файлів адаптерів `--lora`
— див. P8.5) беруть участь у резервуванні та в таблиці байтів за пристроями
(`gpu_weight_bytes`, `cpu_weight_bytes`, `compute_buffer_bytes`,
`kv_bytes`, `mmproj_bytes`, `lora_bytes`, `gpu_total_bytes`).

Перевірено на справжньому заголовку Qwen3-30B-A3B: з 8 GiB VRAM експерти паркуються на
CPU, а щільні шари лишаються на GPU; з достатньою VRAM усі шари йдуть на GPU
(`real_moe_fixture_small_vram_parks_experts_on_cpu`).

## Медіа / VL-контекст (P4.8)

`FitConfig.media` (`MediaFit`) додає токени зображень/відео/аудіо до перевірки
контексту:

```text
media_tokens = frames × tokens_per_frame
             + ceil(audio_seconds) × tokens_per_audio_second
```

Типові значення: 256 токенів на кадр, 25 токенів на секунду аудіо. Якщо `media_tokens > n_ctx`,
вердикт — `NO FIT` (код виходу 2) з `Warning::MediaExceedsContext`.

VRAM: `PlannerConfig.mmproj_bytes` резервується на GPU (так само, як compute/KV).
`--draft PATH` (P5.6) додає розмір файлу чорнеткового GGUF до `mmproj_bytes`, щоб
fit враховував другу модель, хоча декодування й далі використовує n-грами.
`has_mmproj && mmproj_bytes == 0` і далі попереджає, що розмір проєктора не
визначено. Робоча пам'ять енкодера — `frames × n_embd × 4 × 8` через
`estimate_encoder_compute`, і вона додається до резервування на GPU.

## Обмеження NPU (P9.4, Tier 3)

Підтримка NPU — це каркас, що вмикається явно, а не вивантаження обчислень: `llama-cpp-2` не має
бекендів `hexagon`/`openvino` аж до 0.1.154 (огляд у
`docs/versions.md`), тож кожна наведена нижче оцінка для NPU — консервативна заглушка,
а розміщення завжди лишається на CPU/GPU. `runa doctor` показує
`hexagon-stub` / `openvino-stub` лише тоді, коли зібрано з відповідною cargo-функцією;
`RUNA_NPU=hexagon|openvino` вмикає в рядку вердикту `runa auto`
згадку результату перевірки (без цієї змінної вердикт ніколи не
згадує NPU); `RUNA_FAKE_NPU=1|hexagon|openvino` імітує наявність для
тестів, `RUNA_FAKE_NPU=0` примусово робить NPU відсутнім.

- `HwSpec::hexagon()` — 60 GB/s, 45 TOPS, ефективність 0.30 (NPU класу Snapdragon
  X, без калібрування). DSP-ядра Hexagon підкачують ваги через
  вікно ~3.5 GiB: будь-яку модель (або вивантажену частину) понад ~3.5 GiB розглядайте як
  розбиту на кілька вікон, а не як один резидентний блок.
- `HwSpec::openvino()` — 40 GB/s, 13 TOPS (найслабша SKU), ефективність 0.30
  (без калібрування). Лише текстові моделі: шляхи енкодерів зору/аудіо не мають
  валідації на OpenVINO, тож мультимодальні оцінки — лише для CPU/GPU.
- Обидві заглушки орієнтовані на Q4_0: ваги вищої точності на NPU не мають
  виміряної ефективності, тож коефіцієнт 0.30 припускає квантизації класу Q4 і
  занижує прогноз для всього більшого (безпечний напрям для вердикту fit).
- Перекалібруйте (`efficiency`, пропускну здатність, TOPS) за запусками `runa bench` на пристрої,
  перш ніж називати користувачам швидкості NPU; доти вердикт позначає
  їх `(uncalibrated Tier-3 estimate)`.
