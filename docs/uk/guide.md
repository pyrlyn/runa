# docs/guide.md — посібник користувача: що робить кожна можливість, навіщо і як

Приклади для копіювання для прапорців і поведінки. Якщо не зазначено інше,
наведений нижче вивід отримано під час запусків на CPU в macOS на фікстурах із
`tests/fixtures/`. Довідкова документація: `config.md` (кожен ключ),
`fit.md` (формули), `structured.md` (інструменти/MCP), `media.md`
(аудіо/зір), `thinking.md`, `memory.md` (публічний API).

## Відкалібровані прогнози швидкості (`runa bench`, `runa fit`)

**Що.** Прогнози декодування/префілу масштабуються за виміряною історією:
після того як запуск `runa bench` записано, подальші прогнози для тієї самої трійки
`(device, backend, quant)` множаться на медіану відношення виміряне/прогнозоване.

**Навіщо.** Без калібрування похибки моделі сягали 265 % на CPU (M3). Три
калібрувальні запуски на вашому пристрої натомість зводять типові похибки в межі
±15 %.

**Як.** Кожен `runa bench` дописує дані до `~/.runa/calibration.json`
(якщо не задано `--no-calibrate`); `RUNA_CALIBRATION` вказує інше місце.
`bench`, `fit` і `fit --recommend` читають цей файл; порожня або
відсутня база залишає сирий вивід моделі без змін, а один поганий зразок
(нульовий/NaN коефіцієнт) ігнорується для кожної осі окремо.

```sh
runa bench qwen2.gguf --mode cpu --pp 512 --tg 128   # записує зразок
runa fit qwen2.gguf --json                            # тепер прогнози відкалібровані
```

Доведено e2e-тестом `fit_calibration_db_scales_predictions`: зразок із відношенням
виміряне/прогнозоване 2.0× рівно подвоює показану швидкість декодування.

## Робочі потоки (`--threads`)

**Що.** `--threads N` для `run` / `chat` / `bench` / `serve`;
`RUNA_THREADS`; `[defaults] threads` у `runa.toml`. Пріоритет:
прапорець > середовище > файл > вбудоване типове значення.

**Навіщо.** Старе типове значення (усі логічні CPU разом з E-ядрами) програвало
автоматичному вибору потоків у `llama-bench` (M4, 27 %). Тепер вбудоване типове значення
збігається з llama.cpp: P-ядра на Apple Silicon
(`hw.perflevel0.logicalcpu`), логічні CPU деінде.

```sh
runa run model.gguf "hi" --threads 4
# це видно в рядку вердикту:
# runa load ... threads 4 mmap:true mlock:false
```

```toml
# runa.toml
[defaults]
threads = 8
```

`--threads 0` (або некоректні `RUNA_THREADS` / `[defaults] threads`)
завершується помилкою ще до будь-якого завантаження. Лише для GGUF: `--backend mistral` явно
відхиляє цей прапорець, а `run --threads …` оминає демон (прапорець, що впливає на
завантаження, як `--device`).

## Мова транскрибування мовлення (`--lang auto`)

**Що.** `runa media transcribe --lang auto` (типово)
визначає мову й транскрибує за один прохід.

**Навіщо.** Раніше мова визначалася правильно, але повертався порожній транскрипт
(блокер M7): прапорець `detect_language` у whisper.cpp означає
*лише визначити й повернутися без декодування*. Тепер auto передає мову
`"auto"` з незаданим прапорцем.

```sh
runa media transcribe --model base --lang auto clip.wav
# language: en
# (transcript…)
```

Перевірено наживо: вивід `--lang auto` побайтово ідентичний виводу
`--lang en` на тому самому аудіо.

## Кількість токенів міркування (`--json`, serve, `/usage`)

**Що.** Кожна генерація рахує токени тіла міркування
(`Usage.reasoning_tokens`), тож дотримання бюджету (M6) можна перевірити
ззовні:

```sh
runa run qwen3-8b.gguf "What is 2+2?" --think-budget 32 --max-tokens 48 --json
```

```json
{"text":"\n\n2 + 2 equals 4. Here's","usage":{"prompt_tokens":15,"generated_tokens":48,"reasoning_tokens":35,"pp_toks_per_s":77.1,"tg_toks_per_s":15.5},"stop":"max_tokens"}
```

35 ≤ бюджет 32 + grace — ліміт *і* застосовано, *і* показано. Serve показує
такий самий розподіл у непотокових chat completions:

```json
"usage": {
    "prompt_tokens": 9, "completion_tokens": 4, "total_tokens": 13,
    "completion_tokens_details": {"reasoning_tokens": 0}
}
```

`/usage` у чаті дописує `(reasoning N)`, коли N > 0. Бекенди Mistral і хмарні
показують 0 (там немає розподілу на міркування).

## Стискання під час простою в `serve` / `daemon` (M11)

**Що.** Після `idle_timeout_s` (типово 300, `[memory]`,
`RUNA_MEMORY_IDLE_TIMEOUT_S`) без запитів завантажені рушії отримують
задачу простою: кеш промптів LMDB відмаплюється, модель лишається
завантаженою:

```text
serve: idle qwen2-0_5b-instruct-q4_0: prompt cache released (model kept)
```

**Навіщо / обмеження.** CLI та сервери в простої не повинні утримувати відображення
кешу в пам'ять. Виміряно: RSS 772.9 MiB і до, *і* після на моделі 0.5B
— звільнення справжнє, але мізерне порівняно з резидентними
вагами, тож бар'єр M11 (RSS ≤ нижня межа + 10 %) лишається недосяжним
без вивантаження моделі, яке дизайн забороняє. Таймер простою скидають лише ендпоінти
генерації (`chat/completions`, `messages`, `embeddings`,
`transcriptions`); опитування `/health` і `/v1/models`
навмисно його не скидають.

## Потокові виклики інструментів Anthropic (клієнт)

**Що.** Клієнт на `reqwest`+SSE збирає потокові блоки `tool_use`
(`content_block_start` + фрагменти `input_json_delta`) у
ту саму подію `ToolUse`, яку дає непотокова відповідь, ще до
`Done`, тож цикл інструментів CLI обробляє обидва шляхи однаково.

**Чому потоковий режим не типовий.** Лише відповіді цілим повідомленням зберігають
підписи міркування для наступного раунду інструментів; потокові блоки
міркування не несуть жодного підпису, який можна надіслати назад. Тому CLI використовує непотокові
виклики, а шлях SSE лишається коректним запасним варіантом.

## Офлайнові рекомендації з KV + обчисленнями

**Що.** `runa fit --recommend --offline` перевіряє, чи вміщаються розміри файлів каталогу,
без мережі — тепер враховуючи KV-кеш (лінійний за `--ctx`;
`--kv q8_0` удвічі / `q4_0` вчетверо зменшує значення для f16) і
обчислювальний буфер (лінійний за ubatch), а не лише ваги:

```sh
runa fit --recommend --offline --top 5
# runa fit --recommend · VRAM 12 GiB (RUNA_FAKE_VRAM) · RAM 16 GiB · ctx 8192 · kv f16 · offline: sizes only
#  1. gpt-oss 20B                tier 4    ~11 tok/s  FITS CPU
#     runa pull hf:ggml-org/gpt-oss-20b-GGUF:gpt-oss-20b-MXFP4.gguf
#  2. Qwen2.5 VL 7B Instruct     tier 3    ~98 tok/s  FITS GPU
#     ...
```

Довгий контекст на великій моделі більше не «вміщається» офлайн,
водночас не вміщаючись онлайн. `~` позначає оцінки на основі розміру.

## Екранування для серверів MCP (`--mcp`)

**Що.** `--mcp '<command args>'` розбивається за правилами екранування shell:
`'...'` — буквальний рядок, `"..."` дозволяє екранування зворотною скісною рискою, а зворотна скісна риска
поза лапками екранує наступний символ:

```sh
runa run qwen3 "hi" --mcp "python3 'my dir/s.py' --root /tmp"
```

Незакриті лапки є помилкою. Усе складніше (змінні середовища)
задається в `[mcp.servers]` (`docs/config.md`).

## Історія чату між ходами

**Що.** `runa chat` (REPL і `--tui`) з кожним ходом надсилає весь дотеперішній
транскрипт, включно з раундами інструментів:

```text
> My name is Ada.
Hello! How can I assist you today?
> What is my name? Answer with the name only.
Ada
```

Історія обрізається на найстаріші цілі ходи, коли перевищує ~75 % `--ctx`, з
повідомленням `(history trimmed to fit ctx)`. Під час локального завантаження рахуються справжні токени
через власний токенізатор моделі; через сокет демона (токенізатора там немає)
обрізання повертається до оцінки «символи/4» — у будь-якому разі це запобіжник,
бо рушій однаково гучно падає за межами справжнього ctx.
`/reset` і `/model` очищають історію (`/mode` зберігає її: ваги ті самі).
Невдалі ходи нічого не записують, тож повторна спроба надсилає ту саму історію.

## Записи каталогу для split-GGUF

**Що.** Запис каталогу може перелічувати посилання на шарди 2..N у `parts`
(`ref` лишається частиною 1); перевірка підсумовує байти тензорів із заголовків усіх
частин, перш ніж перевіряти вміщення. `size` тоді — сума байтів усіх частин:

```toml
[[model]]
name = "Example 70B split"
ref = "hf:org/model:model-00001-of-00003.gguf"
parts = ["hf:org/model:model-00002-of-00003.gguf",
         "hf:org/model:model-00003-of-00003.gguf"]
size = 42520398432
```

Жодного розділеного запису поки що не постачається (усе, що є в каталозі, вміщається в один
файл); підтримку схеми та перевірки покрито тестами, вона чекає
на першу шардовану модель, що вміститься на обладнання Tier-1/2.

## Виклики інструментів Harmony (gpt-oss)

**Що.** Запити з інструментами рендеряться через власний шаблон моделі,
тож gpt-oss говорить мовою Harmony (`<|channel|>commentary
to=functions.…`), Qwen3 — мовою Hermes `<tool_call>`, а
моделі без шаблону повертаються до узагальненого JSON. Покрито тестами на
справжньому шаблоні 20B в обох порядках заголовків; шаблони з `thinking_forced_open`
не потребують особливої обробки на клієнті (прапорцем володіє llama.cpp,
отримуючи наш `enable_thinking`, — це доведено обов'язковим викликом інструмента Qwen3-8B,
що завершився в межах бюджету міркування 64+8).

## Обмеження навантаження на систему (`--max-load-percent`)

**Що.** Обмеження лише з попередженнями (типово 80 %) на частку загальних
системних ресурсів, яку може використати запуск: `--max-load-percent N` для `run` /
`chat` / `bench` / `serve` / `daemon`, `RUNA_MAX_LOAD_PERCENT`,
`[system] max_load_percent`. Пріоритет: прапорець > середовище > файл.

**Навіщо.** Попередження до того, як велика модель затисне машину: кожне
перевищення друкує практичне `warning:` зі значенням, яке треба встановити.
Запуск завжди продовжується — це ніколи не фатально.

```sh
runa run model.gguf "hi" --threads 16
# warning: system already uses ~924 MiB RAM (91% of 1024 MiB), above
#   max_load_percent=80 — set max_load_percent to at least 91 (...)
# warning: --threads 16 wants ~100% of 16 CPUs, above
#   max_load_percent=80 — set max_load_percent to at least 100 (...)
#   or lower --threads to 12
```

Існує три таких рядки: потреба моделі в RAM (після читання заголовка),
фоновий тиск на RAM і частка CPU для `--threads`. Значення поза діапазоном
завершуються помилкою ще до будь-якого завантаження. Цей прапорець вимикає для `run` використання демона
(демон не знає обмежень на окремий запит) і відхиляється з
`--backend mistral` (там ніколи не попереджає).
