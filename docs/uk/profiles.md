# docs/profiles.md — профілювання та поліглотна оцінка (K3, K4, P5.1)

## K3 — Оцінка поліглотного «запасного виходу» (D19, бар'єр D1)

**Кандидат:** попередня обробка зображень `resize` + `normalize` + `patchify` (P5.4) через
`fast_image_resize` (Rust, чистий) проти C `stb_image_resize` (один заголовковий файл, `cc`).

**Інтерфейс:** `runa-media::image::resize()` належить Rust (`ImageBuf` → `ImageBuf`);
шлях на C був би `runa-media/src/image_c.c` за `#[cfg(feature = "c-resize")]`
з ідентичним `ImageBuf` на вході/виході та диспетчеризацією через `#[cfg]`.

**Бенчмарк (M3 Max, 512×512 RGB → 336×336, 100 ітерацій, `criterion`):**

| Реалізація | середнє | ± | порівняно з Rust |
|------|------|---|---------|
| Rust `fast_image_resize` (типово) | 1.82 ms | 0.04 | — |
| C `stb_image_resize` (`cc -O3`) | 1.79 ms | 0.05 | **+1.7%** |

*Еквівалентність:* `cargo test -p runa-media --test image`, попіксельно `max_diff ≤ 1` (u8) на
`tests/fixtures/shapes.png` і 10 синтетичних градієнтах.

**Бар'єр D1:** C має обійти Rust на **≥5 % наскрізно або ≥2× на ізольованій операції**.
Результат **+1.7%** бар'єра **не** проходить.

**Рішення:** **REJECT** — лишаємо шлях на Rust. Жодного `image_c.c` не злито; інтерфейс
Rust лишається. Переоцінювати під час кожного оновлення тулчейну (D19).

**Інші розглянуті кандидати (поки без бенчмарку):**
- Ресемплінг аудіо `rubato` (Rust) проти `libsamplerate` (C): `rubato` уже
  у 2–3× швидший за `libsamplerate` на x86_64 у попередніх спайках P4.1; шлях на C не потрібен.
- Whisper: `sherpa-onnx` (Rust-обгортка над C++ ONNX) проти `whisper-rs` (C): Parakeet —
  поліглотний кандидат із найбільшою віддачею для P4.2, але він потребує C++-рантайму
  `sherpa-onnx` і завантаження моделі (25 мов). Оцінку відкладено до P4.2.

## K4 — Аудит паралелізму (D20)

**Аудит 2026-09-08 (M3 Max, 4 ядра, `moon run :test` проти `cargo test --workspace`):**

| Шлях | До | Після | Реальний час | Рішення |
|------|--------|-------|-----------|----------|
| `cargo test --workspace` (8 крейтів, послідовно) | `cargo test -p runa-fit && cargo test -p runa ...` | `moon run :test` (паралельно, з кешем, 4 ядра) | 12.3s → 6.1s (2.0×) | Лишаємо moon; джерелом істини лишається cargo |
| `runa doctor --bench` (CPU memcpy, 64 MiB) | однопотоковий `copy_from_slice` | `rayon`, 4 частини `par_chunks_mut` | 0.04s → 0.02s (2×) | Лишаємо rayon; бар'єр D1 пройдено |
| `runa-fit::Fetcher::fetch_header` | синхронний `reqwest::blocking` (поточний) | `reqwest::async` + `tokio` | виграшу в реальному часі немає (читання заголовка обмежене затримкою, один діапазон на обмін) | Лишаємо синхронний (D20: паралелізм, що не зменшує реальний час, прибирається) |
| декодування аудіо в `runa-media` (10 кліпів) | послідовний `symphonia` на кожен файл | `rayon` на кожен файл | 1.2s → 0.7s (1.7×, 4 ядра) | Поки лишаємо послідовне (бар'єр 2× не пройдено); переоцінити на 32 кліпах |

*Не лишилося жодного послідовного гарячого шляху без обґрунтування бенчмарком. Робота, обмежена I/O, лишається синхронною там, де async не допомагає; робота, обмежена CPU, паралелізується за даними там, де виміряно ≥1.5×.*

Таблиця аудиту зберігається тут відповідно до перевірки K4; реальний час `moon run :test` проти `cargo test` записано вище.

## P5.1 — Обв'язка для профілювання (топ-10 операцій для кожного режиму)

**Інструменти (локально + нічний P5.8):**

| Інструмент | Встановлення | Команда |
|------|---------|---------|
| `samply` | `cargo install samply` | `samply record cargo run -p runa-engine --example gen -- tests/fixtures/qwen2-0_5b-instruct-q4_0.gguf "hi"` |
| `cargo flamegraph` | `cargo install flamegraph` | `cargo flamegraph -p runa -- bench tests/fixtures/qwen2-0_5b-instruct-q4_0.gguf` |
| `criterion` (ядра) | dev-залежність у `runa-kernels` | `cargo bench -p runa-kernels --bench softmax` |

**Процедура:** профілюйте pp512 (префіл) і tg128 (декодування) окремо за допомогою `runa bench --json`;
для внутрішніх механізмів ggml використовуйте `samply` на прикладі `gen` або `runa bench` з увімкненими Metal/CUDA.
Записуйте в цей файл топ-10 символів за кількістю зразків для кожного режиму.

**Початковий спайк (M3 Max Metal, приклад `gen`, qwen2-0.5B Q4_0):** у декодуванні домінують
ядра `ggml_metal` (`kernel_mul_mv_q4_0`, `kernel_flash_attn`); семплінг на Rust займає <1 %
реального часу tokens/sec — це узгоджується з порядком D14 (ядро семплінгу — P5.3, воно ще не гаряче).

**Колбеки планувальника ggml:** не під'єднані в закріпленій обгортці `llama-cpp-2` 0.1.133;
повернутися до цього, коли оновлення llama.cpp відкриє стабільні хуки для вимірювання часу кожної операції.

| Режим | Машина | Топ операцій (% зразків) | Примітки |
|------|---------|-------------------|-------|
| декодування tg128 | M3 Max Metal | `kernel_mul_mv_q4_0` ~45%, `kernel_flash_attn` ~30% | із `samply` на `gen` |
| префіл pp512 | — | очікується | запустити `runa bench` + samply |
| декодування на CPU | — | нічний | `.github/workflows/perf.yml` (P5.8; на раннерах GitHub, доки не з'являться self-hosted) |

## P4.9 — Профіль медіаконвеєра (кандидати для P5)

**Машина:** M3 Max, `cargo bench -p runa-media --bench media` (release, criterion, 20 зразків).
**Відтворення:** та сама команда; HTML у `target/criterion/`.
**Flame-графік:** [profiles-p49.svg](../profiles-p49.svg) — ексклюзивний час Rust для кліпу в 5 s (32 VL-кадри + 5 s аудіо 48 kHz, ресемпльованого до 16 kHz). `samply` / `cargo flamegraph` не було в PATH; SVG побудовано із середніх значень criterion нижче, а не із семплованого стеку.

| Операція | Розмір | середнє | кліп 32 кадри / 5 s |
|----|------|------|---------------------|
| `resize_rgb` найближчий сусід 512→336 | один кадр | **73 µs** | 2.3 ms |
| `normalize_rgb` → [−1, 1] | 336² RGB | **42 µs** | 1.3 ms |
| `histogram_l1` (зміна сцени) | пара 336² | **642 µs** | **20.5 ms** |
| `resample_mono` rubato 48 k→16 k | 1 s PCM | **1.38 ms** | 6.9 ms |

**Mel:** у `runa-media` не реалізовано. Whisper.cpp (`whisper-rs` 0.16) будує log-mel усередині C++-рантайму після того, як ми передаємо йому PCM 16 kHz. Ядро mel на Rust/C окупилося б лише в разі відмови від whisper; цього немає в списку P5.

**Рейтинг для P5 (бар'єр ≥5 % e2e або ≥2× ізольовано):**

1. **`histogram_l1`** — ~65 % цього зрізу Rust, у 9× більше за resize. Найкраще ізольоване ядро (гістограма на NEON/AVX). **Не** впливає на e2e VL/ASR (домінують ffmpeg + whisper). Відкладено, доки виявлення сцен не проявиться в samply повного `runa media video`.
2. **`resize_rgb`** — найближчий сусід уже займає 73 µs; високоякісний `fast_image_resize` у K3 займав **1.82 ms** (у 25× повільніше). P5.4 — це заміна заради якості, а не виграш у швидкості порівняно з найближчим сусідом.
3. **`normalize_rgb`** — 42 µs скалярно; NEON SIMD 26.8 µs (**1.52×**, P5.4). Бар'єр D14 — 2× → REJECT, лишаємо скалярний.
4. **`resample_mono`** — K3 уже відхилив `libsamplerate`; rubato лишається.
5. **mel у whisper** — живе в ggml/whisper.cpp; це не задача для `runa-kernels`, якщо тільки ми не замінимо ASR.

**ffmpeg / whisper** (не входять до бенчмарку, порядок величини з P4.1/P4.2/P4.5): декодування + ASR для 5 s аудіо займає від сотень мілісекунд до секунд. Таблиця попередньої обробки на Rust — кілька десятків мілісекунд. Час на P5 слід і далі витрачати на семплінг ggml (P5.3) і, якщо колись, на гістограму сцен — а не на resize/normalize/mel у цьому крейті.
